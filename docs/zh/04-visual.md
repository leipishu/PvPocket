## 1. 设计目标

界面的「平滑感」不来自贴图，而来自四件事，本规范逐条给出可执行的约束：

1. **层次**：近黑表面 + 五级明度阶梯，而不是所有面板共用一个灰。
2. **克制**：一个暖强调色，红色只用于破坏性动作，圆角不超过 6px。
3. **动效**：所有状态切换都有 60–320ms 的过渡，帧率无关。
4. **文案**：一行说完一件事；状态能画出来就不用文字重复。

### 2.5 亮色主题

主页面「设置」页可以切到亮色。亮色**不是把上面五个灰反过来**，是一套并行的完整色板，定义在
`PvTheme.apply(Theme)` 里，两套令牌名字一一对应。

两条硬约束：

- **颜色令牌不能是 `static final`。** javac 会把 `static final int` 内联进调用点，改 `PvTheme`
  的值对已经编译进去的 282 处引用无效——运行时不换肤，只有重新编译才换。所以颜色字段一律是可变的
  `static int`；度量（圆角、行高）与 `MOTION` 也是。
- **亮色下强调色必须压深。** `ACCENT #F5A524` 在白底上只有 1.9:1，而它在 38 处被当文字用
  （版本号、胜场 chip、焦点标签）。亮色主题用 `#FFB26A00`（约 4.6:1），深色主题保持原值。
  同理 `teamInk` 在亮色下向黑混合，否则队伍色在白底上糊成一片。

亮色不是「另一个产品」：表面仍按明度分五级、强调仍是同一个暖色、红色仍只用于破坏性动作。

「设置」页的 `Light theme` 行后面跟一枚 `beta` 胶囊。**标出来，不是藏起来**——亮色色板已经完整到
能用，但也年轻到会改，胶囊说的就是这件事，比第二行没人读的说明省地方。胶囊是 `PvBadge`：14px 高、
3px 圆角、`ACCENT_SOFT` 底 + `ACCENT` 字，和规则面板标题行那枚 `v0`/`v1` 版本标签同一个定义
（后者在 `RuleScreen` 里内联绘制，位置右对齐于按钮，但宽高取自 `PvBadge.widthOf()` 与 `PvBadge.H`，
两枚胶囊不会各自漂移）。宽度在构造时量好写进普通 `width` 字段，否则审计会把它当零尺寸控件。

**度量按 426×240 的逻辑画布定。** 1280×720 窗口在 GUI scale 3 下只有这么大，规则面板实际是
406×220、内容区 172px 高。v0.6 的度量（行高 28、按钮 24、Tab 26、头部 52、页脚 40）是按「大屏」
估的，在那个画布上控件必然溢出——现在压到上表的值，省下的是行高与内缩，字号不动。

列宽一律用 `PvLayout.share(总宽, 比例, 下限, 上限)`，不要写死像素：固定列在窄画布上会把某一列
挤成负数，而 `enableScissor` 不校验矩形，负宽度会反转裁剪区、让子控件画到相邻列上面。行宽低于
190px 时 `RuleRow` 改两行制（标签一行、控件一行），控件宽度另有夹取，任何宽度下都不出本行。

**字号只有一级：1.0×。标题也不靠放大，也不靠粗体。** 早期标题用 `Formatting.BOLD` 加重，但原版
粗体不是字重，是同一字形右移一像素再画一遍：内置位图字体有手做的粗体表，看不出来；资源包里的
TrueType 字体没有，同一段代码就变成「糊了一层」。这个界面本来就是给换过字体的玩家排的版（见
`README` 的字体说明），所以粗体全部撤掉，层级改由颜色（`TEXT` 对 `TEXT_DIM`）与位置（页眉带一条
分隔线）表达。MC 位图字体在 1.3× 这类非整数缩放下会被 GL 重采样，笔画糊成灰边——这是「像素感」的
主要来源之一，同样已废弃。

唯一的位图是主页顶栏的字标（`assets/pvpocket/textures/gui/logo.png`）：它是画，不是控件，所以不走
文字排版。高 20px（顶栏 30），宽 121px，纹理按 3 倍预缩（363×60），在 GUI scale 3 下正好一纹素对
一个物理像素——不要把它拉伸到顶栏，也不要用非整数倍缩放，字标有 1px 描边，任何非整数倍都会把描边
糊成灰边。

例外是**对局比分板**：它不画在面板里，而是浮在世界上方，四档（75% / 90% / 100% / 120%）由玩家在
设置里选，整块一起缩放。理由不同——它不是排版的一部分，而是「挡视野」与「看不清」之间的取舍，
只有坐在那块屏幕前的人知道该往哪边挪。面板里的字号不跟着它变。

**框定控件里的文本按四级阶梯让路：原样 → 缩小 → 换行 → 截断。** 这个界面有两种语言，同一个
标签的英文常是中文的两倍宽，而每个框都是按短的那种量的。阶梯本身在 `PvDraw` 里：

| 级 | 条件 | 结果 |
|---|---|---|
| 1 | `自然宽 ≤ 框宽` | 1.0× 原样绘制 |
| 2 | 缩到 `max(0.75, 框宽/自然宽)` 能放下 | 缩放绘制，仍然一行 |
| 3 | 0.75× 仍放不下，且框高容得下第二行 | 按 1.0/0.9/0.8/0.75 依次试换行 |
| 4 | 换行也放不下 | 在 0.75× 下截断，末尾加省略号 |

- **0.75 是地板，不是偏好。** 正文字高 8px，低于四分之三在 GUI scale 1 下字符就糊成一团；
  「字看不清」比「末尾省略号」更糟。
- **缩小优先于换行。** 只差一点点就放得下的标签仍然占一行——两行制会打乱面板一行一条的节奏。
  只有一行必须截断时才动第二行。
- **两级容差。** 差 2px 以内不算放不下：`0.733` 和 `0.75` 在屏幕上没有区别，为 1.6px 把
  `Accept & start` 变成 `Accept & sta…` 是纯损失。
- 换行只在**高度允许**的地方用：22px 的 chip、24px 的行、20px 的按钮各容两行（16px 的标题行
  chip 只有一行），提示句最多三行且**行高由宽度决定**（`SettingRow.hint` 在 `onWidth` 里算）。
- 尺寸能改的时候改尺寸，不要靠缩小硬塞。`PvCycle` 的标签列、`KeyBindRow` 的标签列、历史行的
  地图名，都是先把装饰性的东西（箭头内距、回合点阵、阶段 chip）让出去，再谈字号。

审计会把「缩了」和「截了」分开报（`labels: N shrunk, M cut`）。**缩了是机制在工作，截了是框
真的不够**——后者带屏名、画布尺寸和「地板上需要多少像素」，照着那条清单改框，不要改字号。

### 3.1 栅格化规则（反像素感）

所有形状都过 `PvRaster`：像素覆盖率取自**有向距离场**，不再取自单轴的内缩量。

```
sdRoundBox(p) = length(max(|p−c| − (h/2 − r), 0)) + min(max(qx,qy), 0) − r
填充覆盖   cov = clamp(0.5 − d, 0, 1)
描边覆盖   cov = clamp(|[d−0.5, d+0.5] ∩ [−t, 0]|, 0, 1)
```

- **为什么一维不够。** 旧实现只算「真边缘落在这一列的哪个位置」，因此知道弧线穿过本行的横向位置，
  却完全不知道本像素在纵向上被曲线切掉了多少。45° 处两者差到四分之一像素的 alpha，而 GUI scale 3
  下一个逻辑像素是 3×3 物理像素——那点差就是可见的台阶。SDF 给的是到边界的**垂直距离**，直边、
  斜边、圆弧同一个公式。
- **不要对 `0.5 − d` 做超采样。** 这个斜坡本身就是像素的盒式滤波；在同一个像素内平均四个斜坡，
  等于把四个 1px 滤波平均成 1.5px，直边上会报出 0.75 而真值是 1.0（这是实现期踩过的坑）。
- **行结构：每行最多三段，不是每像素一段。** 每行从两端各扫到第一个「完全在内部」的像素，中间整段
  一次 `fill`，边界像素按**同色合并成段**再画。合并不是优化细节而是正确性问题：`roundPanel` 的描边带
  在上下两行里横贯整条宽度（那一行整行都在 `[−t, 0]` 内），逐像素发射时 300px 的面板一行就是 300 段，
  一个 300×38 的卡片要 1686 次 `fill`——列表一滚动，每帧几千次填充全花在发四边形上。现在先把边界带
  用距离扫出来、再按同色合并，同一张卡片是 202 段，`roundRect` 是 66 段。实测 93µs → 29µs。
- **同一像素只画一次。** 一行的三段区间互不相交，边界扫描把每个像素恰好交给其中一个发射器。
  `PvRaster.main` 会对此做自检（`roundedRect` 与 `roundPanel` 各一套）：洞像素 = 0、重绘像素 = 0、
  与 8×8 真实面积覆盖率之差 < 0.12、深处必须是纯填充色。改 `PvRaster` 后必须跑一次
  `java -cp build/classes/java/client com.leipishu.pvpocket.client.gui.PvRaster`。
- **描边是内嵌的，不是居中的。** 1px 描边占据形状最外那 1px（`[−t, 0]`），与「先画描边再内缩 1px
  填底」的旧行为一致。居中的 1px 描边只覆盖外圈的一半，读起来比旁边的面板更浅。
- **`roundPanel` 单次合成。** 边界像素同时算填充覆盖与描边覆盖，按比例混合两色，alpha 取填充覆盖。
  两层形状相叠会把羽化的描边边混进羽化的填充边，在每条直边留下半透明错色环。
- **`ring` 不能实现成「外圈实心 + 内圈透明填充」**——`fill` 传 0 表示不绘制，内圈不会被挖空；
  它是用距离带 `[−t, 0]` 算术挖出来的。
- **`chevron` / `plus` / `cross` 保持硬像素**：1.5px 对角线在 scale 1 下会糊成灰，硬像素在任何
  scale 下都是硬像素。

因此所有半透明填充只允许出现在单次绘制内，不得靠多层叠加调色；需要更浓就调 alpha，不要叠两次。

### 3.2 面板分区：镀层 + 凹槽

面板不是「卡片套卡片」，而是两层表面：

1. **镀层（chrome）**：整块面板先按 `SIDEBAR` 填充，圆角 6。顶栏与左侧栏是**同一块表面**，
   因此天然连通，中间没有描边、没有分隔线。
2. **凹槽（well）**：在其上叠一个多圆角矩形，从 `(panelX + 侧栏宽, panelY + 顶栏高)` 到面板右下角，
   填 `PANEL`。左上、右上、左下直角，右下跟面板圆角。

两条约束：

- **镀层与凹槽之间没有任何线条。** 分区只靠明度差（`0x15` 对 `0x0A`）。这也是 `SIDEBAR` 必须比
  `PANEL` 高整整一档的原因：`0x12` 对 `0x0A` 只差 3% 亮度，读起来像脏边而不是分区。
- **分隔线只出现在凹槽内部。** 顶栏底部没有线（颜色台阶就是线），状态行上方有一条 `DIVIDER`，
  它从凹槽左边界起画，不许横穿侧栏。

**侧栏宽由内容推导**：`clamp(max(最长 Tab 标签 + 34, 最长按钮标签 + 16), 72, 100)`，34 = 两侧内缩 12 +
文字缩进 10 + 脏点列 12，16 = 按钮左右各 8。写死宽度在中文下浪费、在英文下截断（"Consumables" 64px）。

**只看 Tab 标签是不够的。** 英文的提交按钮比任何 Tab 都宽（"Accept & start" 84px 对 "Players" 42px），
按 Tab 算出来的 76px 侧栏会把按钮标签截成 "Accept & st…"。因此先建按钮、量出它们的标签宽度、再定
侧栏宽，`init()` 里的顺序是 `buildStack()` → `sidebarWidth(stack)` → `buildActions(stack)`。

**提交按钮竖排在侧栏底部**，主操作贴最下（表单的确认位）。侧栏同时容纳 8 个 Tab 与 3 个按钮时
Tab 会被压到 12px，这是可接受的下限；把 `还原` 这类非提交动作移到状态行、把 `预设 / 编辑配装`
这类「打开别处」的动作移出侧栏，是让这个高度算得过来的前提。判据是**一条竖向预算**：
侧栏高 = 顶栏以下全部，Tab 高 × 条目数 + 按钮高 × 个数 + 间距必须装得下，装不下就先减按钮。

**装不下就换排布，不要继续压。** 8 个 Tab 加 3 个按钮要 213px，而 320×180 的画布上面板只有 160px 高。
`PvTabs.minHeight(n)` 给出还能读的下限（每项 11px），低于它就切 `compact`：Tab 占满整列高度，按钮
排成一行放在凹槽下方，每个按钮取自己标签的宽度。预算算不过来就换排布，这是唯一的出路——继续压
只会先失去可读性，再失去整个按钮。

**侧栏不再有选中指示条。** 选中态由 `CARD_ACTIVE` 铺底一格表达，指针和键盘移动的是同一条高亮。
贴在外沿的 2px 强调条曾经会在 Tab 之间滑动，但它和选中铺底表达的是同一件事，两条一起出现反而
让人以为条是「拖到别处」的独立状态。

## 4. 组件状态矩阵

所有可交互组件必须实现四态，且四态之间必须过渡。

| 组件 | 常态 | 悬停 | 按下 | 选中 | 禁用 |
| --- | --- | --- | --- | --- | --- |
| 主按钮 | 强调实心 + 黑字 | `ACCENT_HOVER` | `ACCENT_PRESSED` + 内缩 1px | — | `ACCENT_DIM` + 弱化字 |
| 普通按钮 | `CARD` + `BORDER` | `CARD_HOVER` + `BORDER_STRONG` | `CARD_ACTIVE` + 内缩 | — | `SUNKEN` + `TEXT_MUTED` |
| 危险按钮 | 无描边，10% 红铺底 + 红字 | 铺底 32% + `DANGER_HOVER` 字 | 铺底 42% + 内缩 1px | — | `SUNKEN` + `DIVIDER` 字 |
| 幽灵按钮 | 无底 | 6% 白底 + 字提亮 | — | — | 弱化字 |
| 开关 | 关：`CARD_ACTIVE` 轨道，无描边 | 轨道提亮 | — | 开：`ACCENT` 轨道 + 白滑块 | `SUNKEN` |
| 滑杆 | 轨道 `SUNKEN` + 强调填充 + 10px 白滑块 | 填充微提亮 + 滑块外 8px 光晕（20% alpha） | 同悬停，光晕保持 | — | `ACCENT_DIM` |
| 步进器 | `CARD` + `BORDER` | 悬停半区抬升为 `CARD_ACTIVE` | — | — | `SUNKEN` |
| chip | `CARD` + 灰字，无描边 | `CARD_HOVER` + 字提亮 | — | `ACCENT_SOFT`(14%) 铺底 + 强调字 | `SUNKEN` |
| Tab | 透明 | `CARD_HOVER` | — | `CARD_ACTIVE` | — |
| 列表行 | 透明 | `CARD_HOVER` ×75% | — | `CARD_ACTIVE` + 2px 强调条 | 弱化字 |

**描边只用于「普通按钮」「步进器」和面板本身。** 有色组件（危险按钮、chip、开关、列表行）一律去掉描边，靠铺底浓度和字色区分状态。原因：有色描边在半透明铺底外再叠一层，视觉上就是一圈「更深的条条」，与 §3.1 是同一个问题的两种表现。

焦点：1px 强调环，绘制在控件外扩 2px 处（`PvDraw.ring`），透明度跟随 `focusT`。旧实现用「外扩一圈半透明矩形」，在黑底上会读成光晕，已废弃。

### 4.1 行内对齐

行是「左信息区 + 右操作区」的两栏结构，右栏右边界固定，不允许各元素各自定位：

| 约束 | 值 | 说明 |
| --- | --- | --- |
| 行右内边距 | 20px | 行卡片右边界到按钮右边界 |
| 按钮与左内容间距 | 12px | 也是比分/元信息的右锚点 |
| 单行文字垂直基线 | `y + (h - 8) / 2 + 1` | MC 字高 8px，取整后 +1 才是视觉居中 |
| 双行文字 | `y + 7` / `y + 20` | 行高 46 时的固定两行槽位 |

比分、计数这类「右侧数字」与按钮同处一条水平中线，不再单独占一行——两行行高里数字沉到第二行就会读成「上不着下不落」。

**两行制的行高由控件推导，不由常量给出。** 标签占住行顶，剩下的才是控件：

```
y + 0  … y + 5    空气
y + 5  … y + 13   标签字形（8px）
y + 13 … y + 14   间隙 1px
y + 14 … y + 14+控件高   控件
                       + 4px 空气 = 行高
```

从行底往上减（`y + height - 控件高 - 6`）曾经是写法，它只在「所有控件一样高」时和标签对齐：
chip 是 22px、步进器是 20px，于是 chip 行的控件从 `y+12` 开始，而标签画到 `y+14`——**控件压住标签最后
两行像素**，只有多选行够高才看得出来。行高必须从控件算起，控件才不会去吃标签。

### 4.2 HUD 选中态

HUD 不参与面板的层次阶梯（它压在游戏画面上，背景不可控），因此：

- 选中槽位 = `CARD_ACTIVE` 铺底 + 1px 强调环（`PvDraw.ring`，圆角 3），**不是**上下两条粗线。粗线在物品图标下会被读成「框断了两边」。
- 环内缩 1px 绘制，与槽位边界留出气口。
- HUD 的淡入用 `appearT` 统一乘到 alpha 上，不做位移。

## 5. 动效规范

实现集中在 `PvAnim`。四个原则：

1. **帧率无关**。`dt = delta × 0.05`，夹在 `[0, 0.1]` 秒。禁止「每帧加固定值」。
2. **阻尼优先**。悬停、按下、焦点、滚动跟随用指数阻尼 `damp(cur, target, dt, tau)`；目标可在中途改变而不产生跳变。
3. **定时补间只用于有明确终点的动作**：开关滑块、面板入场。
4. **只动连续量。** 位置、alpha、铺底浓度都可以动；**绘制尺寸不行**。1.5px 的半径变化只能落在两个
   整数上，底层阻尼再平滑也会读成两级跳变——滑杆悬停曾经把圆点半径从 5 按 `round(hoverT × 1.5)` 涨到 7，
   看起来就是「卡一下」。现在圆点半径恒定，动的是它背后光晕的 alpha（256 级，远低于眼睛的分辨阈）。

| 场景 | 时长 / 时间常数 | 曲线 |
| --- | --- | --- |
| 面板入场 | 160ms | 遮罩与面板黑幕同步 easeOutCubic |
| 悬停填充 | τ 90ms | 指数阻尼 |
| 按下 | 进 40ms / 出 80ms | 指数阻尼 + 1px 内缩 |
| 焦点环 | τ 80ms | 指数阻尼 |
| 开关滑块 | 140ms | easeOutBack（约 10% 过冲） |
| 滑杆填充（键盘） | τ 50ms | 指数阻尼（拖拽时不阻尼） |
| 滑杆光晕 | τ 90ms | 指数阻尼，只动 alpha；悬停与拖拽共用一个目标 |
| chip 选中 | τ 50ms | 指数阻尼，逐 chip 独立 |
| 滚动跟随 | τ 37ms | 指数阻尼 |
| 滚动淡出遮罩 | τ 80ms | 指数阻尼 |
| 提示气泡 | 停留 150ms + 淡入 τ 50ms | 指数阻尼 |
| 比分变化闪烁 | 320ms | 线性衰减到 `ACCENT` |
| 观战红点呼吸 | 2000ms 周期 | 正弦 |

`PvTheme.MOTION = false` 可一键关闭全部动效（所有过渡立即到位）。

## 6. 文案规范

这是本版新增的硬约束，和颜色、圆角同级。

1. **状态不重复表达。** 视觉已经说清的事，文字不再复述。选中态由填充 + 描边 + 强调字表达，不再写「（使用中）」「（已选）」。
   - 例：场地被占用时，步进器用强调字 + 3px 强调标记 + 悬停提示说明原因，标签本身保持原名。
2. **一行一条信息。** 副标题、状态行提示都按「一行」设计，超长即视为设计错误，而不是靠 `fit()` 截断兜底。
3. **长度预算**（按 MC 字体 9px/全角字符估算）：

| 位置 | 预算 | 说明 |
| --- | --- | --- |
| 面板标题 | 4–6 字 | |
| 副标题 | ≤ 14 字 | 与版本 chip 共享一行 |
| 状态行左提示 | ≤ 12 字 | 与配装摘要、还原共享一行 |
| 行标签 | ≤ 8 字 | 右侧留给控件 |
| 提示气泡 | ≤ 40 字 | 超出换行，最多 3 行 |

4. **禁止 emoji 与图形符号字符。** 箭头、加号、叉号一律用 `PvDraw.chevron/plus/cross` 绘制，不依赖字体字形；命令与聊天文本同样不带符号前缀。
5. 标点用全角，间隔用 `·`，省略号用 `…`。

新加一个控件忘了参与布局，它看得见。
