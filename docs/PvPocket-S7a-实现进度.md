# PvPocket S7a 实现进度：配装数据与构造

> 对应需求：**一、关于配装**
> 1. 三大类：武器 / 装备 / 消耗品 / 方块
> 2. 武器按类别显示；剑斧可选材质（**材质只决定显示，不决定属性**）；属性由玩家编辑：伤害、耐久、击退、特殊附魔效果；弓的无限可开关，关了要设箭矢数；钓鱼竿可设是否造成伤害及多少；三叉戟可设是否开启激流
> 3. 装备：护甲和盾牌，可选材质、编辑属性
> 4. 消耗品：常规食物、特殊食物、药水（增益减益，**均为喷溅型**，时长可自定义）
> 5. 方块：可设种类；**羊毛按双方不同颜色**；同页加镐子和剪刀
> 6. 进入战斗后这些物品出现在双方身上
> 7. 每一小局结束物品恢复到最初状态
> 8. GUI 要显示物品图标
>
> 本阶段（S7a）交付 **1–7 的数据与落地**，第 8 条（图标 GUI）是 S7b。

## 二、数据模型

### 2.1 类别与页面

| 页面 | 类别 |
|---|---|
| 武器 | 剑、斧、弓、弩、三叉戟、重锤、钓鱼竿 |
| 装备 | 头盔、胸甲、护腿、靴子、盾牌 |
| 消耗品 | 食物、药水 |
| 方块 | 方块、**镐**、**剪刀** |

镐和剪刀按需求放在方块页——它们的用途是处理场地，不是战斗。

### 2.2 材质只影响显示

这一条是整个配装系统里最容易做错的地方。

原版铁剑自带 `attribute_modifiers`：`+6 攻击伤害`。如果配装只是**追加**一个修饰符，那么"材质不影响属性"就是假的——玩家把伤害设成 5，实际打出来还是 5+6。

所以 `LoadoutBuilder.applyAttributes` 是**整体替换** `ATTRIBUTE_MODIFIERS` 组件：

```java
AttributeModifiersComponent.builder()
    .add(GENERIC_ATTACK_DAMAGE,
         new EntityAttributeModifier(id("loadout.damage"), 总伤害 - 1.0, ADD_VALUE),
         MAINHAND)
    .build();
```

`总伤害 - 1.0` 是因为玩家空手基础伤害是 1.0，物品提供的是增量。玩家在面板上填"7"，打出来就是 7。

**代价**：材质换成下界合金不会更耐打、不会更快。这正是需求要的，但需要在面板上说清楚，否则玩家会以为下界合金有隐藏加成。

### 2.3 一行配装的全部字段

```java
ItemKind kind;        // 类别
Material material;    // 材质（无材质的类别忽略）
String   variant;     // 食物 id / 药水效果 id / 方块 id
int count;            // 数量 1..64
int slot;             // 0-35 背包，36-39 护甲，40 副手，-1 自动分配
int damageTenths;     // 总攻击伤害 ×10，0 = 保持原版
int armorTenths;      // 护甲值 ×10
int durability;       // 0 原版 / -1 不可破坏 / >0 指定上限
int knockback;        // 击退等级 0..3
int flags;            // WeaponFlag 位掩码
int arrowCount;       // 弓没有无限时的箭矢数
int durationSec;      // 喷溅药水时长
int amplifier;        // 药水等级 - 1
```

扁平结构是刻意的：每个字段正好是编辑器里的一行，也正好是编解码要往返的一项。嵌套结构只会多一层映射，换不来任何能力。

### 2.4 编码

```
<转义后的名字>~kind|material|variant|count|slot|damage|armor|durability|knockback|flags|arrows|duration|amplifier;...
```

字段顺序**冻结**：它同时是客户端/服务端的传输格式和磁盘上的存档格式。加字段只能往末尾加（解码容忍字段不足），改顺序不行。

名字里只有 `~` `;` `|` `%` 四个字符需要转义，用最小映射就够。

### 2.5 指纹

和规则集用同一套构造（SHA-256 前 6 字节 hex）。配装是双方协商的一部分，所以打一场有争议的对局时，可以拿日志里的 `LOADOUT_APPLIED digest=...` 去复现当时实际发下去的配装，而不是某一方记得的那套。

## 三、特殊效果：用原版附魔，不自己实现

| 开关 | 附魔 | 适用 |
|---|---|---|
| 横扫 | `sweeping_edge` | 剑 |
| 无限 | `infinity` | 弓 |
| 火矢 | `flame` | 弓 |
| 冲击 | `punch` | 弓 |
| 激流 | `riptide` | 三叉戟 |
| 穿透 | `piercing` | 弩 |

`WeaponFlag.appliesTo(kind)` 不是装饰。给剑提供"无限"会造出一把带无效附魔的剑，玩家会以为自己配置了什么。编辑器只显示该类别真正能用的开关。

击退单独用一个字段映射到 `knockback` 附魔等级 0–3——这和 1.8 的击退 I/II 是同一套语义，不是妥协。

## 四、消耗品

### 4.1 食物

白名单 9 项：金胡萝卜、牛排、熟猪排、熟鸡肉、面包、烤马铃薯、金苹果、附魔金苹果、牛奶。

### 4.2 药水

**全部是喷溅型**（`Items.SPLASH_POTION`），效果用 `potion_contents` 的 `custom_effects` 自定义：

```java
new PotionContentsComponent(
    Optional.empty(),                                  // 不用预设药水
    Optional.of(PotionContentsComponent.getColor(...)), // 颜色由效果推导
    List.of(new StatusEffectInstance(effect, 秒*20, amplifier)))
```

白名单 19 项效果，增益 12 / 减益 7。刻意**没有**漂浮、黑暗、不祥之兆这类会破坏决斗或无法自解的效果。

瞬间治疗 / 瞬间伤害的时长为灰显——这两类效果完全忽略时长，给它们一个能拖的滑块等于骗人。

### 4.3 方块与羊毛

方块白名单 15 项，第一项是 `minecraft:white_wool` 并且标为「按队伍染色」：

```
玩家 0 → minecraft:red_wool
玩家 1 → minecraft:blue_wool
```

只有这一个哨兵 id 会被改写。玩家如果主动选了某个具体颜色，那个选择优先。

## 五、物品真正落到身上的时机

这是 S7a 里唯一改动会话流程的地方，也是唯一有数据风险的地方。

```
accept → ARENA_LEASED → freeze（写快照）→ ROUND_READY → startRound
                                                          ├─ 传送到出生点
                                                          ├─ 设最大生命
                                                          ├─ 清空背包 + 发配装   ← 这里
                                                          └─ ROUND_ACTIVE
settle → 清掉落物 → RESTORING → 恢复快照 → 回写地形 → 释放租约
```

**必须在快照之后。** 快照是生存背包唯一的副本；先发配装再拍快照，等于把配装当成玩家自己的财产存了进去，局末恢复时玩家会凭空多出一套铁剑和羊毛。

对应地，`LoadoutBuilder` 提供两个方法，不能混用：

| 方法 | 行为 | 用途 |
|---|---|---|
| `grant` | **清空背包**再写入 | 开局发装 |
| `give` | 只往空位放，不动已有物品 | `/pvpocket loadout give` 测试用 |

把"清空背包"和"给点东西"合成一个方法，早晚会在错误的场合被调用。

## 六、校验

`Loadout.validate()` 返回逐行的人类可读问题，空列表表示可发放。客户端每次编辑都跑一遍（保证保存按钮诚实），**服务端收到时再跑一遍**（客户端不是可信来源）。

校验项：

| 项 | 规则 |
|---|---|
| 条数 | 1 – 36 |
| 槽位 | 不能重复 |
| 物品解析 | `材质_类别` 必须存在于物品注册表 |
| 数量 | 1 – 64 |
| 伤害 | 1.0 – 40.0 |
| 护甲 | 0 – 30 |
| 耐久 | 0 / -1 / 1 – 10000 |
| 击退 | 0 – 3 |
| 箭矢 | 0 – 64 |
| 药水 | 效果在白名单内，时长 1–300 秒，等级 0–4 |
| 食物 / 方块 | 在白名单内 |
| 附魔开关 | 必须适用于该类别 |

## 七、槽位自动分配

```
护甲：靴 36 / 腿 37 / 胸 38 / 头 39
盾牌：副手 40
其余：快捷栏 0-8 → 主背包 9-35
```

已经带槽位的条目保持不动——玩家的摆放是配装的一部分，每次编辑都重新推导会让物品在光标下乱跳。

## 八、验证状态

### 已验证

- `./gradlew build` 通过
- 服务端启动无错误（`Done (1.167s)`，0 条 ERROR/Exception）
- 指令树注册正常：`/pvpocket loadout [give]` 出现在帮助里

### 未验证（需要真人开客户端）

- 配装物品的属性是否真的按填的值生效（伤害、耐久、击退、护甲）
- 材质是否真的只影响外观（换材质后伤害不变）
- 无限开关：开 → 无箭可射；关 → 32 支箭出现在背包
- 喷溅药水的效果与时长
- 羊毛是否按双方红/蓝染色
- 局末快照恢复后，配装物品是否完全消失（没有残留、没有复制）
- 地形保护下玩家亲手挖方块的否决提示

### 已知缺口

1. **没有自定义组件**。v0.5 §1.3 里提到的 `pvpocket:loadout_spec` 没有做。当前用原版组件覆盖能覆盖 90% 的需求；剩下三件事做不到：
   - 击退精确到 0.1（附魔只有 0.5 步进）
   - 盾牌的减伤比例（1.8 格挡是硬编码 `(1+x)*0.5`）
   - 钓鱼竿的"击中造成伤害"其实是靠 `attack_damage` 属性实现的，能生效，但无法单独标成"只在击中时"
2. **配装还没有进入协商**。双方各自拿到默认预设，看不到对方的配装，也没有"修改后重新征询"。这是 S7c。
3. **`d.loadoutScope`（每人独立 / 每队统一）没有执行**，目前一律每人独立。
4. **`d.allowConsumables` / `d.allowPickup` / `d.allowCrafting` 没有执行**。
5. **配装不能保存为预设**，每次都是默认预设的副本。
6. **没有上限总量校验**。36 行 × 64 个方块是 2304 个方块，能直接把场地堆满；`f.allowPlace` 默认关，所以暂时无害，但开方块模式时要加总量限制。
