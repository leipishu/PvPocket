# 主页面（Home）方案 · 草案

> 状态：**已实施**（2026-11-08）。本文是当时的方案草案，保留原始判断与取舍，**不是规范**。
> 现行规范见 `docs/zh/05-usage.md`（使用）、`docs/zh/03-architecture.md`（协议与存储）、
> `docs/zh/04-visual.md`（亮色主题）。
>
> 目标：给 PvPocket 一个**客户端入口**，把目前只能靠指令触达的能力收进 GUI。
>
> **审阅结论（与草案不同之处）：**
>
> 1. 时间放**顶栏**，不占首页正文（草案原本放在首页）。
> 2. 亮/暗切换：接受。
> 3. 「负」用灰色而非绿色：接受。
> 4. 数据属于服务器、换服即清零：接受，本来就是意图。
> 5. 历史每人 200 场：接受。
> 6. **指令一律保留。** §9 的「删除 `/pvpocket duel`、`list`、`loadout edit`、`spectate <前缀>`」
>    没有执行——控制台与 RCON 没有客户端，脚本与运维只能走指令。主页面是**多一条路**，
>    不是唯一的路。
>
> 实施结果另有两处偏离草案：预设页的「编辑」没做（只做了开始/分享/导入/删除）；
> 历史海报导出没做（先做了逐局详情弹窗 + 复制一行结果）。

---

## 0. 结论摘要

**做**：一个新的顶层界面 `HomeScreen`（热键 / 背包按钮打开），复用现有「镀层 + 凹槽」骨架与侧栏
Tab，五个页面：首页 / 数据 / 历史 / 预设 / 设置。为此新增 3 个 payload、1 个服务端统计模块、
1 个本地客户端配置文件。

**不做**：不做成就系统、不做社交（好友/战队）、不做跨服云同步、不做亮色 HUD。

**最大的一处判断**：这个界面上线后，`/pvpocket duel`、`/pvpocket list`、`/pvpocket loadout edit`
就都该删掉了。这不是副作用，这正是目的（见 §9）。

> **这条判断被否决了。** 指令全部保留：控制台、RCON、脚本与运维都没有客户端，
> 「面板能做的指令就不该有第二条路」这条既有约定只适用于**玩家侧**的重复入口，
> 不适用于「没有界面时的唯一入口」。

## 1. 现状盘点：五条硬约束

在动手前必须先承认这五件事，它们决定了方案的形状。

| # | 事实 | 代码位置 | 后果 |
| --- | --- | --- | --- |
| 1 | **现在没有任何界面能被客户端主动打开** | `PvPocketClient` 里所有 `setScreen` 都由 S2C payload 触发 | 热键必须新增「C2S 请求 → S2C 数据」这条路，或先开空壳再拉数据 |
| 2 | **对局面板不是独立界面** | `RuleScreen` 由 `RulesOpenPayload` 构造，`sessionId`/`role`/`rules` 全在包里 | 「发起决斗」不能自己拼界面，只能请求服务端调 `openRoster()` |
| 3 | **统计不存在** | 全仓库 `grep stats\|kills\|damageDealt` 无命中 | 数据页与历史页要从零建服务端采集 |
| 4 | **预设是纯客户端的，且已经完整** | `PresetStore`（`config/pvpocket/presets.json`）、`PresetShare` | 预设页几乎无服务端工作量，可最先交付 |
| 5 | **主题是 `static final int` 常量** | `PvTheme`，282 处引用 / 25 个文件 | javac 会把常量**内联进调用点**，不改 `final` 就不可能运行时换主题 |

第 5 条要展开一句：`public static final int PANEL = 0xF70A0A0B;` 是编译期常量，所有
`PvTheme.PANEL` 在 class 文件里已经是字面量。**运行时改字段不会生效**，必须去掉 `final`
（或改成方法）。去掉 `final` 后 282 处调用点一行都不用改——这是唯一低成本的路径。

## 2. 导航模型

### 2.1 三层结构

```
游戏
 └─ HomeScreen            ← 热键 / 背包按钮（仅在无界面时可用）
     ├─ 发起决斗 ────────→ RuleScreen（服务端推来，替换主页）
     ├─ 进行中 → 观看 ───→ 直接切观战，关界面
     ├─ 历史 → 详情 ─────→ 详情 Overlay（模态，不换界面）
     ├─ 预设 → 编辑 ─────→ 预设编辑界面（无会话模式，Phase 3）
     └─ 设置 → 按键捕获 ─→ 行内捕获态（不换界面）
```

### 2.2 需要给 `PvScreen` 加一个 `parent`

现在只有 `LoadoutScreen(payload, parent)` 有"从哪来回哪去"的概念，其余界面 `close()` 一律
`setScreen(null)`。主页存在之后，`RuleScreen` 的 Esc 应该是「回主页」还是「回游戏」，取决于
它是怎么被打开的。

**建议**：`PvScreen` 增加 `protected PvScreen parent`，`close()` 改为
`client.setScreen(parent)`（`parent == null` 时回游戏）。改动量约 6 行，收益是之后每个子界面
都不用再各写一遍返回逻辑。

**例外**：由服务端**主动推送**打开的界面（邀请、对局结束）不带 parent，关闭即回游戏。理由：
邀请是打断性的，把它关掉之后玩家想看的是战场，不是菜单。

### 2.3 热键的触发条件（重要）

```java
if (client.currentScreen != null) return;   // 有界面就不响应
if (client.player == null) return;          // 标题界面/断开时不响应
```

第二条不只是防御：头像要用 `client.player` 的皮肤，统计数据要按 uuid 查，主菜单下这三样都没有。
一个在主菜单能打开、但头像空白、数据全零的主页，比不能打开更糟。

## 3. 骨架：主页面外壳

### 3.1 复用现有镀层/凹槽，不新造表面

直接继承 `PvScreen`，`chromeH = 30`，`chromeW = sidebarWidth()`，
`drawPanelFrame()` 原样生效。**不新增任何表面色**，不画任何描边——这是现有规范里最不容妥协的
一条（`04-visual.md` §3.2）。

### 3.2 侧栏结构

```
侧栏（chromeW ≈ 84–96）
├─ 头像行 34px
│   ├─ 头像 22×22（圆角 3）
│   ├─ 玩家名（9px，fit 到剩余宽度，完整名走 tooltip）
│   └─ 右侧一个 3px 状态点：绿=LIVE 在场 / 灰=旁观 / 红=对局中？
├─ 8px 空白            ← 不是分隔线。分隔线只许画在凹槽内部
├─ Tab × 5 × 24px + 4px 间距 = 124px
└─ 余量（426×240 下约 24px）：够则放一个 18px 幽灵「关闭」，不够就不放
```

**竖向预算验算**

| 画布 | 面板高 | 可用（去顶栏） | 头像 34 | 空白 8 | Tab | 余量 |
| --- | --- | --- | --- | --- | --- | --- |
| 426×240 | 220 | 190 | 34 | 8 | 5×24+4 = 124 | **24** |
| 320×180 | 160 | 130 | 34 | 8 | 5×17+4 = 89 | **−1** |

窄画布下 Tab 压到 17px（下限 11），刚好卡住。所以**关闭按钮不进侧栏**，改放顶栏右侧：
标题「口袋决斗」左对齐，右侧依次是时间（见 §4.1）和一个 16×16 的 `PvDraw.cross` 关闭热区。
这样窄画布不需要 `compact` 排布，省掉一整套分支。

### 3.3 头像怎么画

`ctx.drawTexture` + `PlayerSkinDrawer.draw(ctx, textures, x, y, 22)`，
textures 取自 `client.getSkinProvider().getSkinTextures(client.player)`。

两个要点：

1. **皮肤是纹理绘制，不是物品绘制**，走 GUI 层 z=0，能被遮罩盖住——不像 `ctx.drawItem`
   那样在 z=150 的深度测试层里盖不住（见 `PvDraw.itemsVisible` 的注释）。所以弹窗存在时
   头像可以正常变暗，不需要额外处理。
2. 皮肤纹理可能未加载。兜底：画一个 `CARD_ACTIVE` 圆角块 + 玩家名首字母（大写，居中）。

## 4. 五个页面

统一约定：内容区 306×190（426×240 下），内边距 16 → 可用 **274×158**。
所有页面都提供三态：**有数据 / 空 / 加载中**（加载中只画一行 `TEXT_MUTED`，不做骨架屏——
骨架屏在这个尺寸下只会闪烁）。

### 4.1 首页

**一处需要你拍板**：时间放哪里。我的建议是**放顶栏右侧**，不放正文。

理由：正文可用高度只有 158px，而首页要装「问候 + 鼓励语 + 主按钮 + 进行中 + 最近一局」五块。
时间独占一行 26px，占掉 16%，而它是**环境信息**——玩家扫一眼就知道，不需要停在首页才能看。
放顶栏还顺带解决了「切到数据页就看不了时间」的割裂感。

若你希望严格按「首页显示时间」理解，改成正文首行即可，代价是下面五块要压到 132px（需要砍掉
"最近一局"卡片）。

```
顶栏：口袋决斗（粗体）        2026-11-08 周日 · 21:47        [×]

正文（274×158）
y+0    晚上好，Dev1                              TEXT
y+14   今天的手感，值得再来一局。                TEXT_DIM，≤28 字，单行
y+38   ┌──────────────────────┐
       │   发起一场决斗        │  148×28，ACCENT 实心，ON_ACCENT 字
       └──────────────────────┘
y+74   ────────────────────────────────  DIVIDER（凹槽内，从凹槽左边界起）
y+82   进行中的对局                          右侧 "2 场"（TEXT_MUTED）
y+94   行 ×2，每行 30px：地图 · 模式 · 回合 2/7 · 1:0        [观看] 52×20
y+154  最近一场  3:1 胜 · 斗兽场 · 2 天前                    [查看]
```

**空态与降级**

| 情况 | 表现 |
| --- | --- |
| 没有进行中的对局 | 该区块折成一行「暂无进行中的对局」，最近一局卡片上移 |
| 没有历史 | 「最近一场」整块不画 |
| 玩家已在对局中 | 主按钮变为 `DANGER` 描边的「返回当前对局」+「投降」两个 18px 按钮；发起按钮禁用并给 tooltip 说明原因（`openRoster` 里已有的三种拒绝理由） |
| 玩家在观战 | 主按钮禁用，顶部加一行「正在观战 · 按 X 解除」 |
| 未连服务端（`canSend` 为假） | 主按钮禁用 + 一行「当前服务器未安装 PvPocket」 |

**鼓励语**：`pvpocket.home.greeting.<id>`，id 是 1..12 的**整数常量表**，随机取 id 再翻译。
不要随机取"语言文件里的第 n 个键"——中英键数一旦不一致就会取空。同一个 id 在一次会话内保持不变
（换页回来不该换句子，那会显得界面在抽风），跨会话才重新抽。

### 4.2 数据

两列 × 三行卡片，卡 133×42，间距 4，顶部 18px 筛选行。42×3 + 8 + 24 = 158，刚好用完。

```
[全部] [近 30 天]                                    （右上，两枚 chip）

┌─────────────┬─────────────┐
│ 总场次       │ 胜率         │
│ 42          │ 54.8%        │   ← 数值粗体 1.0×，标签 TEXT_MUTED
└─────────────┴─────────────┘
│ 胜场 23      │ 总击败 74    │
│ 回合 96/51   │ 总伤害 1820  │
└─────────────┴─────────────┘
│ KD 1.09      │ 最长连胜 7   │
└─────────────┴─────────────┘
```

- **近 10 场胜负条带**：10 个 8×8 方块，胜 = `ACCENT` 实心，负 = `CARD_ACTIVE`，无描边
  （有色组件不描边）。放在筛选行右侧或第三行卡片下方——这是这个尺寸下唯一读得懂的图表，
  折线图在 158px 高里没有意义。
- 数值格式：伤害不带小数（HP 整数），KD 两位小数，胜率一位小数。空数据显示 `—`。
- **320×180 降级**：两列会把卡片压到 96px，`总伤害 1820` 就放不下。窄画布改**单列滚动**，
  六张卡纵向排。这是 `PvScrollPane` 的既有能力，不需要新逻辑。

### 4.3 历史

```
工具栏 24px：最近对局（粗体）            [全部][胜][负]
────────────────────────────────────────────
行 42px × 3 可见，滚动
┌──────────────────────────────────────────┐
│ 3:1  胜   斗兽场 · 1.8 · 2v2    [详情]   │  ← 比分粗体，结果 chip
│ 11-06 21:03 · vs Dev2,Dev3 · ▪▪▫▪        │  ← 小局点 6×6，最多 15 个
└──────────────────────────────────────────┘
```

- **结果色**：胜 = `ACCENT_SOFT` 底 + `ACCENT` 字；负 = `CARD` 底 + `TEXT_MUTED` 字。
  **不用红绿**——红色在本项目里专属于破坏性动作，借用它表示"输"会污染语义。这是与常见
  战绩界面最不一样的一处，需要你认可。
- 小局点：每局一个方块，胜/负/中断三色。比写「2-1-0-1」省一半宽度，也更一眼。
- 点击行 → **详情 Overlay**（`PvScreen.overlay`，不是 append 到 roots）：

```
详情 360×232
标题：对局详情                      [×]
斗兽场 · 1.8 · 2v2 · 11-06 21:03 · 用时 12:22
3 : 1                    （比分，粗体）
─────────────────────────────
第 1 局  Dev1 胜   死亡   1:32
第 2 局  Dev2 胜   出界   2:05
第 3 局  Dev1 胜   死亡   1:58
第 4 局  Dev1 胜   投降   0:41
──────────────────────────────
Dev1, Dev4  vs  Dev2, Dev3
──────────────────────────────
[复制文本]  [导出海报]              [关闭]
```

- **记录上限**：服务端每人保留 **最近 200 场**，超出丢最旧（见 §6.3）。UI 一次取最近 30 场
  的完整明细（含每局），更早的靠"加载更多"。
- **导出海报**（见 §8，是全文风险最高的一项）。

### 4.4 预设

```
[配装 3] [规则 2]                        [导入] [新建]
──────────────────────────────────────────────────
行 36px：
  长弓速攻                    [开始] [更多]
  3 天前 · 12 项
──────────────────────────────────────────────────
```

- 顶部两枚 chip 切换 `PresetKind`（配装/规则），带数量。**不做左右两栏**：306px 分两栏后每栏
  148px，放不下"名字 + 元信息 + 两个按钮"。
- 行内两个按钮：`开始`（52×20 普通按钮）、`更多`（28×20 幽灵按钮，画 `PvDraw.plus` 转 45°…
  不行，规范禁图形字符且只有 `plus/cross/chevron` 三个图元——用 `chevron` 向下 + 文字"更多"）。
- `更多` → 小型 Overlay 菜单：重命名 / 覆盖保存 / 分享 / 删除（`DANGER`）。删除必须二次确认，
  且确认按钮是 `DANGER` 实心——这是全界面唯一的红色实心按钮。
- **从预设开局**：
  - 规则预设：确认框「用这套规则创建对局？之后仍需选择对手」→ 发送 → 服务端
    `openRoster(player)` 后把该规则套进新 draft，`rulesRevision` 从 0 起 → 面板切到 RuleScreen
    的**名册页**（不是规则页：规则已经定了，下一个问题是"谁打"）。
  - 配装预设：「开始」= 打开名册 + 把自己的 loadout 设为该预设。理由：一场对局不能只由一方的
    配装决定，但"我带着这套配装去开局"是玩家真实的意图。
- **编辑**：见 §7.3，是 Phase 3 的独立工作项，Phase 2 只做重命名/覆盖/删除/分享/导入/开始。

### 4.5 设置

滚动列表，五个区块。每区块 = 一行粗体标题 + 若干 24px 行。

| 区块 | 内容 |
| --- | --- |
| 关于 | 图标 32×32（`assets/pvpocket/icon.png`，`drawTexture` 缩放）+ `PvPocket` 粗体 + 版本 chip + `LGPL-3.0-only` + 「在浏览器打开源码」幽灵按钮 |
| 外观 | 主题 `[暗色][亮色]` 两枚 chip；动效 `[开/关]` 开关（写 `PvTheme.MOTION`） |
| 按键 | 打开主页 / 切换观战视角 / 解除附身，每行右侧一个 96×20 的"键帽"按钮 |
| 数据 | 本机预设 5 条 · 配置目录 `config/pvpocket`（只读文本）+ 「打开目录」 |
| 诊断 | 「打开界面审计」？不行，那是启动参数。改为：客户端版本 + 服务端是否支持（`canSend` 三项）|

**版本号**取 `FabricLoader.getInstance().getModContainer("pvpocket")`，不要在代码里写死字符串。

**协议**：`LGPL-3.0-only` 与 `fabric.mod.json` 一致。jar 里不带 LICENSE 全文，所以「查看」只能
打开仓库链接——这是一次**外部动作**，按钮文案要写明"在浏览器打开"，不要伪装成站内跳转。

**按键绑定**（这是你特别要求的一项，细节最多）：

```
行：打开主页                      [ P ]
点击 → 该行按钮变成 [ 按下按键… ]，底色 ACCENT_SOFT
  ├─ 收到任意键 → 冲突检测 → 写入 → 行恢复
  ├─ Esc        → 取消（不恢复原键，恢复绑定前状态）
  └─ 30 秒无输入 → 自动取消
```

写入路径（**同步覆盖到原版按键绑定**，即写进 `options.txt`，不另存一份）：

```java
binding.setBoundKey(InputUtil.fromKeyCode(keyCode, scanCode));
KeyBinding.updateKeysByCode();       // 重建 code→binding 索引
client.options.write();              // 落到 options.txt
```

三个必须处理的点：

1. **冲突检测**。原版允许两个功能绑同一个键且不提示。这里要拦：若目标键已被任何 `KeyBinding`
   占用，行下方红字提示「已用于：跳跃」，并**拒绝写入**。拒绝而不是覆盖——覆盖等于悄悄改掉
   玩家的移动键。
2. **按住不放的键**（Shift/Ctrl）。`InputUtil.isKeyPressed` 在捕获态要跳过这些键，否则玩家
   按 Shift 想切输入法就直接被绑走。
3. **鼠标键不在此列**。只处理键盘，鼠标绑定继续走原版界面。理由：自绘 GUI 的鼠标事件已经被
   面板消费，捕获鼠标键会和"点击按钮"本身冲突。

## 5. 网络层：三个新 payload

沿用现有风格：扁平字符串编码（`|` 分隔字段、`\n` 分隔行），不引入嵌套 record 的 codec。
`MatchListPayload` 已经证明这套编码够用且好排查。

| 方向 | 名称 | 内容 | 触发 |
| --- | --- | --- | --- |
| C2S | `HomeRequestPayload` | 无字段（或 `flags`） | 打开主页时请求一次；下拉刷新 |
| S2C | `HomeStatePayload` | 统计 + 最近 30 场（含每局）+ 进行中对局 + 待处理邀请 | 应答 |
| C2S | `HomeActionPayload` | `action:int` + `arg:String` | 发起决斗 / 从预设开局 / 打开某场观战 |

`action` 取值：`0 = OPEN_DUEL`、`1 = OPEN_DUEL_WITH_RULES`、`2 = OPEN_DUEL_WITH_LOADOUT`。
观战复用已有的 `SpectateRequestPayload`，不新增。

**为什么不是一个 payload 拉全部**：主页打开是热路径（玩家可能反复开关）。`HomeStatePayload`
一次约 10KB（30 场 × 300B + 统计），可以接受；但**不要在打开界面时同步阻塞**——先画本地数据
（预设、设置、头像、时间），统计区显示"加载中"，payload 到了再填。理由见 §1 约束 1：
客户端现在没有"自己开界面"的先例，第一次做要选延迟最低的那条路。

**幂等与顺序**：`HomeRequestPayload` 可能在 200ms 内连发两次（玩家快速开关）。服务端按 uuid
节流到 1 秒一次，重复请求直接丢弃，不回包。**不要**给 `HomeStatePayload` 加版本号——统计是
全量快照，后到的覆盖先到的就是正确答案。

## 6. 数据层：统计与历史

这是全案工作量最大、且**上线后最难改**的一块。口径必须先冻结。

### 6.1 存储布局

在现有 `<world>/pvpocket/` 下新增两个目录：

```
stats/stats.json                 全局计数（一个文件，几十个玩家量级）
history/<uuid>.jsonl             每人一个 append-only 文件
```

`stats.json` 用 `PvPocketStorage.writeAtomically` 整体重写（与 `PresetStore` 同策略）；
`history/<uuid>.jsonl` 用 `SessionJournal` 的追加写法，一行一场，天然容忍截断尾部。

**为什么历史按人分文件**：读的时候永远是"某个人的最近 N 场"，一人一个文件是一次顺序读；
写的时候只追加一行，不需要重写别人的记录。一个共享文件会让每次写都变成全量重写。

### 6.2 口径定义（需你确认）

| 指标 | 定义 | 采集点 |
| --- | --- | --- |
| 总场次 | **完成的 series 数**。进入过 `ROUND_ACTIVE` 且终止（含投降/掉线判负/强制结束）算一场；`DRAFT`/`VOID`/`SESSION_DROPPED` 不算 | series 终止唯一收口处 |
| 胜场 | 该 series 的胜方包含此玩家 | 同上 |
| 胜率 | 胜场 / 总场次，0 场显示 `—` | 派生 |
| 回合 / 回合胜率 | `ROUND_ENDED` 计数 / 其中胜方为自己所在队 | `ROUND_ENDED` |
| 总造成伤害 | **仅 `ROUND_ACTIVE` 内、对敌队玩家、护甲后、吸收前**的最终伤害 | `LivingEntity#applyDamage` HEAD |
| 总击败 | 致死伤害的 attacker 是自己 | `SessionManager#onDeath` |
| 死亡 | 自己在 `ROUND_ACTIVE` 内死亡 | 同上 |
| KD | 击败 / max(1, 死亡)；死亡为 0 显示击败数 + `—` | 派生 |
| 最长连胜 | series 级别的连续获胜场数峰值 | series 终止 |

**伤害采集的技术选择**：`LivingEntity#applyDamage(DamageSource, float)` 的 HEAD 是"护甲之后、
生命值扣除之前"，`amount` 就是最终值。比 `allowDamage()` 准（后者只回答"允不允许"，实际伤害
可能被格挡、被吸收）；比 `onDamaged` 好（那时 `getHealth()` 已经变了，要反推）。

一个已知偏差要写进文档：**吸收（金苹果）的伤害也算"造成"**，因为 `applyDamage` 在吸收扣减之前。
我认为这是对的（玩家的攻击确实生效了），但要在 tooltip 里说清。

**不采集的**：PvE 伤害、队友伤害（本来就拦了）、练习模式、观战。

### 6.3 容量与清理

- `history/<uuid>.jsonl`：超过 **250 行**时重写成最近 **200 行**。重写是低频操作（每 50 场一次），
  用 `writeAtomically`。
- `stats.json`：不清理。玩家退服也不删——历史战绩是玩家资产。
- 估算：200 场 × ~280B ≈ 56KB/人。50 人服务器约 2.8MB。可接受。

### 6.4 幂等

series 终止可能被走到两次（正常结束 + `reconcile` 兜底）。历史行里带 `id`（sessionId），
写之前查该玩家文件末尾 20 行是否已有同 id；有则跳过。**不要**只靠内存标记——重启就会重复。

## 7. 预设页的落地方式

### 7.1 Phase 2（可先交付）

`PresetStore` 已经提供 `of/find/put/remove`，`PresetShare` 提供发布/取回，`PresetOverlay`
提供单条保存/导入的交互。Phase 2 只做**列表 + 四个动作**：开始 / 重命名（= 用新名字 `put`
再 `remove` 旧名）/ 删除 / 分享 / 导入。这一阶段**零服务端改动**（除了 `开始`）。

### 7.2 「开始」需要的服务端支持

`SessionManager` 新增两个入口（内部复用 `openRoster`）：

```java
public void openRoster(ServerPlayerEntity p)                        // 已有
public void openRosterWithRules(ServerPlayerEntity p, String rules) // 新增
public void openRosterWithLoadout(ServerPlayerEntity p, String loadout) // 新增
```

`openRosterWithRules` 必须在 `openRoster` **之后**套用规则，因为 `openRoster` 可能命中
"已有 draft → 重新打开"分支（`findOpenSession` 那条）。那个分支是**不能绕过**的：它正是
"崩溃后还能拿回草稿"的保障。所以语义定为：**打开草稿后，用预设覆盖其规则并 `rulesRevision++`**，
而不是新建一个 session。

`openRosterWithLoadout` 只改自己的 `Participant.loadout`，不碰规则。

### 7.3 「编辑」为什么单独放 Phase 3

规则预设的编辑需要 `RuleScreen` 的编辑主体脱离"会话"存在：现在它依赖 `RulesOpenPayload`
（`role`/`revision`/`sessionId`）和提交流程（`RulesSubmitPayload`），而预设编辑没有对手、没有
revision、提交目标是本地文件。

两条路：

| 方案 | 做法 | 成本 | 风险 |
| --- | --- | --- | --- |
| A（推荐） | 把 `RuleScreen` 的页面构建抽成 `RuleEditor` 组件（`buildRows` + 行控件），`RuleScreen` 与新的 `PresetEditorScreen` 各自持有一个 | 中，约 300 行搬迁 | 抽取期间规则面板回归风险，必须靠审计 + 双端联调兜住 |
| B | 预设编辑只开放"重命名/覆盖"，规则本体必须进对局才能改 | 低 | 玩家无法离线调规则，功能不完整 |

配装预设的编辑相对简单：`LoadoutEditor` 已经是可复用的模态组件，只要给它一个"确定 → 写回
`PresetStore`"的 listener 即可，不依赖会话。

**建议**：Phase 3 先做配装编辑（B 的成本、A 的效果），规则编辑按方案 A 单独立项。

## 8. 导出海报（风险最高的一项）

**做法：不做离屏渲染，做"海报态 + 截图 + 裁剪"。**

1. 详情 Overlay 里的「导出海报」把界面切到 `PosterScreen`：整屏 `SCRIM` 全黑（不画世界），
   正中一个固定逻辑尺寸 **320×200** 的海报版式（比分、地图、模式、时间、双方名单、每局结果、
   模组名与版本）。
2. 等 `openProgress() == 1` 后，在**下一帧**调 `ScreenshotRecorder.saveScreenshot`。
3. 回调里用 `NativeImage.read` 读回 PNG，按
   `(panelX, panelY, panelW, panelH) × window.getScaleFactor()` 裁剪，写到
   `screenshots/pvpocket/duel-<sessionId>.png`。
4. 完成后回到详情 Overlay，状态行提示文件名。

**四个必须写进实现的技术点**：

- `saveScreenshot` 是**异步**的，返回 `CompletableFuture`，裁剪必须链在 `thenAccept` 里，
  不能紧跟着下一行读文件。
- 入场动画没结束就截图，会拍到半透明的面板。必须等 `openT` 满。
- 分辨率 = 320×200 × GUI scale。scale 1 只有 320×200，字会糊；scale 3 是 960×600，够用。
  **不做** `ctx.getMatrices().scale(2,2,1)` 强行放大——位图字体被 GL 重采样就糊了，这是规范
  §3 明确禁止的。海报页因此要加一行小字提示「导出分辨率取决于界面缩放」。
- 海报版式必须注册成 `auditVariant`，否则它是唯一一个没人审计过的布局。

**替代方案（更省事，但结果差）**：让玩家自己按 F2 再自己裁。不推荐——"导出海报"是个产品
承诺，不能退化成"你自己截"。

## 10. 我额外建议的功能

按"性价比 / 与目标的相关度"排序，都还没进上面的页面规格。

1. **对局结束自动进主页的结果页**（强烈建议）。现在一局打完是往聊天栏刷几行字，玩家想复盘的
   唯一路径是 `/pvpocket` 命令。把 series 结束做成"自动打开历史详情页"，玩家当场就能看到比分
   与每局明细，历史页也第一次有了天然入口。成本：1 个 S2C payload（复用 `HistoryDetailPayload`），
   风险：打断性，需要 3 秒后可关闭 + Esc 直接关。
2. **待处理邀请卡片**（建议）。现在邀请是**强制弹面板**（`RulesOpenPayload` → `setScreen`），
   玩家正在对局或观战时这个面板会被顶掉，邀请等于丢失。首页加一个"邀请 1 条"卡片能补上这个洞。
   成本：服务端要把"待处理"也放进 `HomeStatePayload`；UI 只是一行。
3. **一键复制战绩文本**（成本极低）。详情页一个按钮，把
   `PvPocket · 斗兽场 2v2 · 3:1 胜 · vs Dev2,Dev3` 写进剪贴板，方便贴到群里。
   `client.keyboard.setClipboard`，10 行代码。
4. **近 10 场胜负条带**（已并入数据页）。这是 158px 高里唯一能读的图。
5. **今日战绩微卡**（首页右上）。「今日 3 胜 1 负」比任何长文本都更能让人有打开欲望。
   需要历史行带时间戳——本来就有。
6. **不做的**：成就/称号、赛季重置、排行榜（需要跨玩家聚合，与"每人对局"的数据模型冲突）、
   好友系统（社交图谱是另一个产品）。

## 11. 风险与取舍

| 风险 | 影响 | 处置 |
| --- | --- | --- |
| **亮色主题是伪需求陷阱** | 38 处 `ACCENT` 当文字用、78 处 `TEXT` 族；`ACCENT`(#F5A524) 在白底上只有 1.9:1，直接不可读 | 亮色必须新增 `ACCENT_INK`/`DANGER_INK`/`TEXT_*_LIGHT` 一组令牌，并逐处替换"强调色当文字"。**这不是翻五个灰值**。建议：亮色只作用于面板，HUD 永远深色（HUD 压在任意地形上，亮底会在雪地/沙漠上失效）；审计加亮色变体，布局数 60 → 90+ |
| 主题常量被 javac 内联 | 不改 `final` 就换不了主题，且症状是"改了没反应" | 去掉 `final`（282 处调用点零改动），`PvTheme.apply(Theme)` 统一赋值；`MOTION` 同样处理 |
| 统计口径不可重算 | 上线后改口径 = 历史数据全废 | §6.2 先冻结并写进 `docs/zh/02-rules.md`；`stats.json` 带 `version` 字段，未来迁移有据可依 |
| 数据随服走 | 换服归零，玩家会觉得"我的战绩没了" | 在数据页底部写一行"统计属于当前服务器"；不做本地累计（两份真相必然对不上） |
| 导出海报分辨率受 GUI scale 限制 | scale 1 下海报糊 | 海报页明示；不做矩阵放大 |
| 邀请与主页抢屏 | 玩家在主页时邀请到达，主页被替换 | 明确规则：邀请优先。`HomeScreen` 不注册任何"被替换后恢复"的逻辑，避免两个界面互相顶 |
| 审计规模膨胀 | 5 页 × 2 画布 + 2 弹窗 = 12 个新布局，审计从 ~2 分钟到 ~3 分钟 | 可接受；但**每个页面必须注册 `auditVariant`**，否则新页面等于没测 |
| 数据页在窄画布溢出 | 两列卡片在 320px 下放不下数字 | 窄画布切单列滚动（§4.2 已写） |

## 12. 分阶段实施

| 阶段 | 范围 | 服务端改动 | 验收 |
| --- | --- | --- | --- |
| **P0 骨架** | `HomeScreen` 外壳、侧栏头像、5 个 Tab、热键、`PvScreen.parent`、5 个空页面、审计变体 | 无 | 热键开合、Tab 切换、Esc 返回、`audit-ui.sh` 退出码 0、中英双语各看一次 |

| **P3 数据 + 历史** | 服务端统计采集与存储、历史写入与幂等、数据页、历史页、详情、导出海报、配装预设编辑 | 统计模块 + 2 个 payload | journal 与 `stats.json` 对账；同一场不被写两次 |

服务端，可以并行；P3 最重且口径要冻结，放最后设计定稿之后。

## 13. 需要你拍板的五件事

1. **时间放顶栏还是正文首行？**（我建议顶栏，正文高度不够）
2. **主题只作用于面板、HUD 永远深色，是否接受？**（我建议接受）
3. **战绩的"负"用 `TEXT_MUTED` 而不是绿色，是否接受？**（我建议接受，红色在本项目专属破坏性动作）
4. **统计归属服务器、换服归零，是否接受？**（我建议接受，不做本地累计）
5. **历史上限 200 场/人 是否合适？**（估算 56KB/人）

另有一个我拿不准的：**首页是否需要"继续上次草稿"入口**。`openRoster` 已经能在有草稿时把面板
还给玩家，但玩家不知道草稿存在。加一行"未完成的对局草稿 · 继续"成本很低，但会让首页多一个
状态分支。倾向：**P4 再做**，先看 P1 上线后玩家会不会自己发现。
