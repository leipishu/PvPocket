## 0. 先按"可逆性"重排

决策的紧迫程度不取决于它有多重要，而取决于**选错之后能不能改回来**。按这个维度重排：

| 层级 | 决策 | 反转成本 | 何时必须定 |
| --- | --- | --- | --- |
| **不可逆（选错要重构）** | D-01 场地承载、D-09 多人模型、D-05 崩溃恢复语义 | 高 | 进入阶段 2 之前 |
| **半可逆（改范围/改模型）** | D-02 保真度、D-06 配装权限、D-03 客户端策略 | 中 | 进入阶段 3 之前 |
| **可逆（改配置）** | D-04 模式冲突、D-07 死亡统计、D-08 场地环境 | 低 | MVP 实现时随手定 |

**结论：把讨论预算集中在第一层。** 第二层给出方向即可，第三层可以留空由实现时决定。

## D-01 场地承载方式（不可逆）

### 选项的真实代价

**选项 ①：世界内区域**

在主世界划一块矩形/多面体区域，玩家走过去就能打。

需要拦截或处理的事件清单（这不是完整的，只是能立刻想到的）：

| 类别 | 具体向量 |
| --- | --- |
| 方块变更 | 破坏、放置、耕地踩踏、作物生长、草蔓延、树叶 decay、雪/冰形成 |
| 爆炸 | TNT、苦力怕、床、重生锚、末地水晶、火焰弹 |
| 物理传导 | 活塞推拉（可跨边界）、流体流动、沙子/沙砾下落、脚手架 |
| 火焰 | 点燃、蔓延、雷击引燃、营火 |
| 实体生成 | 自然生成、刷怪笼、村庄、袭击、史莱姆区块 |
| 实体移动 | 怪物走进来、动物、船/矿车、掉落物、经验球、其他玩家 |
| 容器与红石 | 箱子/漏斗/发射器/投掷器/潜影盒、红石信号跨边界、侦测器 |
| 玩家行为 | 死亡掉落、拾取、末影箱、交易、合成、附魔、铁砧 |
| 环境 | 区块加载/卸载、天气、时间流逝（睡觉跳夜）、结构生成 |
| 第三方 | 任何模组新增的方块实体与交互 |

**关键性质：这个清单是开放的。** 每加一个模组、每升一个版本，都可能引入新向量。你无法通过"写完清单"来关闭风险，只能通过"持续维护清单"来控制风险。而漏掉一项的后果是：**生存世界被污染**，这是产品承诺的根本违背。

**选项 ②：口袋维度**

一个独立维度，场地从模板生成。

需要管理的向量是封闭的，大致只有这些：

| 类别 | 具体向量 |
| --- | --- |
| 进入/离开 | 传送的正确性、传送瞬间的失败回滚 |
| 生命周期 | 维度内玩家掉线、维度区块卸载、服务器关闭时玩家仍在维度内 |
| 内容物 | 维度内生成的实体/掉落物/经验球的清理 |
| 外部插件 | 地图插件、领地插件、备份插件对未知维度的处理 |
| 玩家误留 | 玩家通过非常规手段（末影珍珠、传送指令、其他模组）离开场地 |

**关键性质：这个清单是封闭的。** 因为"那里本来什么都没有"，所以不存在"外面的东西跑进来"和"里面的东西漏出去"——这两类问题在架构上被消除了，而不是被拦截了。

### 判断依据

隔离的可靠性可以粗略写成：

> 可靠性 ≈ 1 − (遗漏向量数 × 单向量泄漏概率)

选项 ① 的"遗漏向量数"是一个随时间增长的开放值；选项 ② 的"遗漏向量数"是一个有限且可枚举的值。**这不是"哪个更安全"的偏好问题，而是"风险是开放式还是封闭式"的结构问题。**

### 代价对比

| 维度 | 世界内区域 | 口袋维度 |
| --- | --- | --- |
| 隔离确定性 | 中，依赖清单完备性 | 高，架构级消除 |
| 每局重置 | 需记录方块 diff 并还原（流体、方块实体状态难还原） | 按模板重建，或整块替换 |
| 崩溃后最坏情况 | 主世界出现未还原的方块变更 | 场地作废重建，生存世界无影响 |
| 服主搭建成本 | 低（就地建） | 中（需导入模板，但只做一次） |
| 玩家感知 | 高（走过去就能看） | 中（需传送，但"打完世界没变"的叙事更强） |
| 观战 | 天然支持（站在外面看） | 需传送观战者进维度 |
| 领地插件 | 冲突（保护 vs 需要交互） | 通常不覆盖，但仍需绕过未注册维度的默认拒绝 |
| 备份体积 | 不变 | 增加（维度数据在存档内） |

### 建议

**选 ② 口袋维度。**

理由排序：
1. 它把本项目最大的技术风险（事件防火墙的完备性）从"开放式"变成"封闭式"。这是唯一一条能让"隔离优先"这个信条真正落地的路径。
2. 它让"每局重置"从"还原一场事故"变成"重新生成一个房间"，正确性从"依赖 diff 记录"变成"依赖模板"。
3. 它与产品名"口袋"的语义一致：一个可以随时打开、随时合上的空间。

### 反转条件

出现以下任一情况时，应重新考虑：
- 目标服主明确要求"竞技场必须在主城旁边、玩家走过去就能看到"（可见性是硬需求）。
- 观战是核心卖点而非附属功能（世界内区域的旁观体验天然更好）。
- 团队对维度注册、跨维度传送的经验不足，而项目周期很紧（此时选 ① 是务实的降级，但必须在文档中承认隔离风险）。

### 选错的后果

- 若选了 ① 而清单不完备：生存世界被污染，玩家物品/建筑受损，产品信任一次性破产。这类事故几乎无法通过"打补丁"挽回口碑。
- 若选了 ② 而可见性是硬需求：功能不满足运营诉求，但**数据是安全的**，可以后续补一个"世界内镜像观战台"来缓解。

**两种错误的性质不同：一个是数据事故，一个是体验缺失。这是建议选 ② 的核心理由。**

## D-02 1.8 保真度目标（半可逆）

### 玩家说的"1.8 手感"到底是什么

拆开来看，玩家对 1.8 的记忆由三件事构成，权重极不均匀：

| 构成 | 权重 | 所在层级 |
| --- | --- | --- |
| 连击节奏（无冷却，点击即出伤） | 高 | F1 |
| 击退位移（W-tap、连击的推拉感） | 高 | F1 |
| 右键剑格挡（减伤 + 减击退） | 高 | F1 |
| 暴击/横扫规则、攻击音效 | 中 | F1 |
| 武器伤害数值、护甲减伤公式 | 低（感知弱） | F2 |
| 附魔/药水/饥饿的具体数值 | 极低 | F3 |
| 命中判定时序、网络包时序 | 极低但"说不清哪里不对" | F3 |

**关键判断：F1 覆盖了约 80% 的体感，但 F1 单独上线会产生一个尴尬的混合体——"1.8 的节奏 + 1.9 的数值"。**

具体表现：护甲收益曲线是现代公式（有韧性、非线性），而攻击是 1.8 的连击频率。结果是"穿铁甲的人在 1.8 节奏下比记忆中更耐打"或"更脆"，硬核玩家会立刻指出"伤害不对"。这类反馈最难处理，因为玩家说的没错，而你也无法解释"我们只做了手感层"。

### 三个层级的成本

| 层级 | 需要接管的东西 | 成本 | 能否收敛 |
| --- | --- | --- | --- |
| F1 | 攻击冷却结算、击退曲线、格挡状态与减伤、暴击条件、横扫规则、音效 | 中（5–6 个结算点） | 能 |
| F2 | 上述 + 伤害管线接管 + 护甲减伤公式重建 + 保护类附魔的减伤方式 + 耐久消耗速率 | 中高（且需与配装系统联动） | 能 |
| F3 | 上述 + 附魔表 + 药水表 + 饥饿与回血节奏 + 碰撞箱 + 命中判定时序 | 极高 | **不能**（部分依赖客户端预测，服务端无法单方面复刻） |

### 建议

**选 F1 + F2 核心项（武器伤害表、护甲减伤公式），明确不做 F3。**

并且做一件比技术选择更重要的事：**改措辞。**

- 不要说"1.8 模式"，说"**Legacy 1.8 手感**"。
- 在游戏内提示、文档、服务器宣传里都写清"手感近似，非逐 tick 完全一致"。

措辞即范围声明。承诺"模式"会招来"你这不是 1.8"的对比；承诺"手感"则把讨论限定在可交付的范围内。

### 反转条件

- 若目标用户是硬核 1.8 PvP 社群（对数值极其敏感）：F2 必须做全，且需要一份公开的数值对照表接受审视。
- 若目标是休闲 SMP：F1 单独上线也可接受，但要在 UI 上弱化"1.8"这个词，改用"经典战斗"。

### 选错的后果

- 承诺 F3 而做不到：永久性的"手感不对"反馈，无法收敛，且每次版本升级都会被重新提起。
- 只做 F1 却宣称"1.8"：短期口碑损失，但可通过补 F2 挽回。

## D-03 客户端策略（半可逆）

### 纯服务端到底缺什么

把缺口逐项列出来，会发现它们全是"呈现"问题，没有"功能"问题：

| 缺口 | 严重度 | 纯服务端替代方案 | 替代效果 |
| --- | --- | --- | --- |
| 剑格挡无姿态（看不到自己在格挡） | 中 | 音效 + 粒子 + 动作栏状态提示 | 约 70% |
| 无格挡 HUD | 低 | 动作栏文字 | 约 60% |
| 攻击指示器（现代样式） | 低 | 用攻速属性驱动，指示器自然表现为"瞬间充满" | 约 90% |
| 无区域边界可视化 | 中 | 粒子墙 / 告示牌 / 地面材质 | 约 60% |
| 无配装编辑 GUI | 中 | 指令 + 聊天菜单 + 成书 | 约 50% |
| 无倒计时 HUD | 低 | title / bossbar / 音效 | 约 95% |

**结论：纯服务端的体验降级是"不够精致"，不是"不能玩"。**

### 三个选项的真实差异

| 选项 | 分发门槛 | 体验上限 | 维护成本 |
| --- | --- | --- | --- |
| 纯服务端 | 零 | 中 | 低（一套代码） |
| 服务端 + 可选增强包 | 零（不装也能玩） | 高 | 中（两套渲染路径 + 版本同步 + "装了/没装"的组合测试） |
| 强制客户端 | 高（Fabric + 模组分发 + 版本对齐） | 最高 | 高（任何客户端崩溃都是你的问题） |

### 建议

**MVP 纯服务端；P2 做可选增强包。**

理由：
1. SMP 场景下，让玩家为了"打一架"去装 Fabric 模组，摩擦远大于收益。服务器里有大量"只玩原版客户端"的玩家，强制客户端等于把他们排除在功能之外。
2. 可选增强包的价值被低估了：它不影响"能不能玩"，只影响"好不好看"，因此可以慢慢做、可以晚发布、可以在体验不足时作为补丁。
3. 但**不要把客户端永久排除**。如果未来要做精确的 1.8 视觉复刻（格挡姿态、挥击动画、命中反馈），客户端是唯一路径。所以架构上要预留"客户端可选连接"的位置，而不是假设永远没有客户端。

### 反转条件

- 若产品定位转向"竞技向服务器"：强制客户端反而是优势（统一体验、反作弊、精确同步）。
- 若配装系统成为核心卖点：GUI 的必要性上升，可能提前到 P1。

## D-04 模式冲突默认值（可逆）

### 三个策略的社交后果

| 策略 | 表面语义 | 实际后果 |
| --- | --- | --- |
| `either_legacy` | 任一方想打 1.8 就打 1.8 | 想打 1.8 的人拥有**单方面决定权**，可用来压制只会现代战斗的对手 |
| `challenger_decides` | 发起方定规矩 | 符合很多社群习惯，但被挑战者只有"接受/拒绝"两个选择，容易形成"只能按对方规矩打"的压迫感 |
| `must_agree` | 必须双方一致 | 最公平，但摩擦最高——很多请求会在协商阶段失败 |

### 建议

**默认 `must_agree`，同时提供"服务器预设"（服主可锁定策略，玩家不可改）。**

理由：
- 公平性争议的代价远高于"多协商一次"的摩擦。决斗产品的核心价值是"双方都觉得公平"，一旦有单方面决定权，输的一方永远有一个现成的解释。
- 实际运营中，服主通常希望统一规则，而不是让玩家自由选择。所以"服务器预设 + 玩家在预设内协商"比"完全自由"更贴近真实需求。

### 附带要求

无论选哪个策略，**必须把最终采用的模式写进会话日志**。事后争议时，"当时用的是哪个模式、由谁决定"必须是可查的事实，而不是双方的记忆。

## D-05 崩溃后处理（不可逆）

### 续赛到底需要什么

要让"崩溃后接着打"成立，必须在崩溃瞬间持久化并能在重启后重建：

| 需要持久化的东西 | 难点 |
| --- | --- |
| 双方血量、饥饿、饱和度 | 相对简单 |
| 双方精确坐标、朝向、速度 | 简单 |
| 每个药水效果的剩余时长 | 简单但易漏 |
| 背包逐格内容与耐久 | 简单 |
| 场地内所有掉落物与经验球 | 难（需要重建实体并保持 ID 映射） |
| 场地方块变更 diff | 难（若选世界内区域） |
| 比分、当前局数、计时器剩余 | 简单 |
| 回合内已消耗的冷却状态 | 易漏 |
| 观战者列表与位置 | 简单 |

**真正的问题不是"能不能存"，而是"存下来的东西重建后是否与崩溃前逐项一致"。** 任一项不准，都会产生一局"看起来公平但实际不公平"的对局，而玩家一旦怀疑结果被操纵，信任就无法恢复。

### 成本收益

| 方案 | 成本 | 收益 |
| --- | --- | --- |
| 一律回滚作废 | 玩家损失一局（重开 < 1 分钟） | 恢复逻辑简单、可验证、幂等 |
| 尝试续赛 | 永久性的正确性负担 + 每次版本升级的回归成本 | 玩家少打一局 |

### 建议

**一律回滚作废，不做续赛。**

并且把"作废"做得体面：
- 明确告知双方"本次系列赛因服务器中断作废"，并展示中断前的比分。
- 提供一键"按原配置重开"的入口，把损失压到一次点击。
- 会话记录保留（比分、参与者、中断原因），只是状态标记为作废，不删除。

### 反转条件

- 若产品面向赛事/竞技场景（一局的价值远高于一次点击）：需要续赛，但那时应该重新设计为"可检查点恢复"，而不是在现有模型上打补丁。

### 选错的后果

- 选了续赛但实现不准：玩家感知为"我明明赢了却判我输"，这是最难挽回的信任损失。
- 选了回滚但产品转向赛事：需要重构恢复模型，成本高但方向清晰。

## D-06 配装创建权限（半可逆）

### 三个选项的真实差异

| 选项 | 防滥用 | UGC 生态 | 运营负担 |
| --- | --- | --- | --- |
| 玩家自由创建（仅受上限约束） | 弱（依赖参数上限） | 强 | 高（需处理"破坏性配装"投诉） |
| 仅服主白名单 | 强 | 无（P2 的分享/导入导出失去意义） | 低 |
| 混合：规则集 + 玩家在范围内自定义 | 强 | 中强 | 低 |

### 混合方案的具体形态

服主定义"配装规则集"，包含三样东西：
1. **可用物品池**（哪些物品能出现在配装里）
2. **参数范围**（移速 0.08–0.15、攻速 1–16、附魔等级上限……）
3. **必选项与禁止项**（例如"必须穿满四件护甲"或"禁止携带末影珍珠"）

玩家在规则集内自由组合。这是"沙盒内的沙盒"——把防滥用从"事后审核"变成"事前约束"。

### 建议

**选混合，但 MVP 降级为"服主白名单 + 玩家可微调有限参数"。**

理由：混合方案的实现成本最高（需要参数范围校验、规则集管理、错误提示），但它是唯一能在"防滥用"和"UGC 生态"之间取得平衡的模型。MVP 先做白名单是为了让决斗本身跑通，规则集在 P1 补齐。

### 反转条件

- 若目标服务器是小型私服（玩家互相信任）：自由创建即可，规则集是过度设计。
- 若服务器有公开排名或经济系统：白名单更稳妥。

## D-07 决斗死亡是否计入生存统计（可逆）

### 问题不在"记不记"，在"别人知不知道"

技术现实：**取消死亡掉落是容易的，阻止第三方插件感知死亡是困难的。** 因为所有插件监听的是同一个死亡事件。你可以在自己的处理里取消掉落、取消重生惩罚，但无法阻止另一个插件在同一个事件里记录"XX 死亡了"、发送死亡消息、或者累加死亡计数。

因此这个决策的真实含义是：

| 选项 | 语义 | 需要做的事 |
| --- | --- | --- |
| 计入 | 决斗中的死亡是"真死亡"，只是不掉落 | 什么都不用做，最省事 |
| 不计入 | 决斗中的死亡对生存世界"不存在" | 需要拦截自己系统内的记录 + 尽可能拦截第三方感知（做不到 100%） |

### 建议

**默认"不计入"，并明确这是"尽力而为"而非"保证"。**

理由：
- "零风险"是产品承诺的核心部分。如果死亡统计会涨，玩家会觉得"还是留下了痕迹"，产品叙事出现裂缝。
- 但必须诚实：第三方插件（死亡消息、死亡坐标记录、死亡计数排行）的感知无法完全拦截。这一点应写进文档的已知限制，而不是假装解决。

### 反转条件

- 若服务器使用死亡统计做经济惩罚/奖励：计入更合理。
- 若服务器有"死亡次数"排行榜：不计入会被质疑"决斗可以刷低死亡数"（虽然决斗有冷却，但仍需评估）。

## D-08 场地是否需要环境危害（可逆）

### 一个比原建议更好的折中

原建议是"纯平坦竞技场"，理由是还原简单。但纯平坦会让产品显得单薄，而且"所有决斗都在同一个空房间"会削弱重复游玩意愿。

**更好的折中：静态地形 + 禁止方块交互 + 无环境危害（掉落伤害可配）。**

| 方案 | 还原复杂度 | 产品感 | 判定复杂度 |
| --- | --- | --- | --- |
| 纯平坦 | 极低 | 低 | 低 |
| **静态地形（预先搭建、不可破坏）** | **低**（地形不变，无需 diff 还原） | **中高** | 低中 |
| 动态地形（可破坏/放置） | 高（需 diff + 流体 + 方块实体还原） | 高 | 高 |

关键洞察：**"有地形"和"地形会被改变"是两件事。** 静态地形能提供地图多样性（高低差、掩体、不同尺寸），却不引入任何还原负担——因为它本来就不会变。

### 建议

**MVP = 静态地形 + 禁止破坏/放置 + 无环境危害（掉落伤害作为可配项，默认开启）。**

这样既避免了"空房间"的单薄，又把还原复杂度保持在最低。

### 反转条件

- 若目标玩法包含"破坏方块"（如搭桥、挖坑）：必须做动态地形，还原机制成为核心功能。
- 若场地承载选口袋维度：动态地形的还原成本大幅下降（整块重建），可以提前支持。

## D-09 多人（>2）是否在路线图（不可逆）

### 成本差异全在"现在怎么设计"

| 设计方式 | 现在成本 | 未来改造成本 |
| --- | --- | --- |
| 会话持有"参与者集合"，比分按参与者记录 | 几乎为零 | 低 |
| 会话持有"玩家 A / 玩家 B"两个字段 | 零 | 高（日志格式、比分模型、判定逻辑、观战模型全部要改） |

### 为什么"预留"几乎免费

因为"2 人"和"N 人"在**会话、回合、快照、日志**这四个层面是同构的：每个参与者一份快照，每回合每个参与者一份开局状态，判定产生一条结果记录。真正的差异只在**判定规则**（2 人是零和，N 人是"最后存活"或"队伍对抗"）和**配装分配**。

也就是说：**数据模型可以通用，判定逻辑不能通用。** 所以预留数据模型、不实现判定逻辑，是正确的切分。

### 建议

**预留但不实现。** 具体含义：
- 会话、回合、快照、日志都按"参与者集合"设计。
- MVP 在协议层明确拒绝 > 2 的会话（给明确错误提示，不是静默失败）。
- 判定逻辑只实现 2 人零和。

### 反转条件

- 若明确永不做多人：可以简化为双人字段，省一点心智负担。但节省的成本极小，不建议为此放弃扩展性。
