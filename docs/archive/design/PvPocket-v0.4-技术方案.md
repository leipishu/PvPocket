## 1. 工程结构

### 1.1 多平台目录策略

```
PvPocket/
├── docs/
└── fabric-1.21.1/        ← 一个「加载器 + 游戏版本」组合一个独立 Gradle 工程
```

理由：后续增加 NeoForge 或 1.21.4 时，各自独立构建、独立版本矩阵、独立发布产物，不会互相污染。代价是共享代码需要复制或抽取——**当前阶段不做共享抽取**，因为 Fabric 与 NeoForge 在 1.21.1 的 API 差异还没有被实际代码验证过，过早抽象会抽出错误的边界。等第二个平台真正落地时，再按实际重复的部分反向抽取。

### 1.2 版本矩阵

| 项目 | 版本 | 说明 |
| --- | --- | --- |
| Minecraft | 1.21.1 | 目标版本 |
| Fabric Loader | 0.16.9 | 与同机其他 1.21.1 工程一致，已验证 |
| Fabric API | 0.116.17+1.21.1 | 1.21.1 分支最新 |
| Yarn | 1.21.1+build.3 | 官方映射 |
| Loom | 1.11.8 | 要求 Gradle 8.14+，与 8.14.3 配套 |
| Gradle | 8.14.3 | wrapper 固定 |
| Java | 21 | 1.21.1 硬要求 |

### 1.3 源码集划分

采用 Loom 的 `splitEnvironmentSourceSets()`：

| 源码集 | 内容 | 加载侧 |
| --- | --- | --- |
| `main` | 会话、沙盒、战斗结算、存储、协议定义、指令 | 双端 |
| `client` | 自绘 GUI、HUD、战斗反馈渲染、客户端预测 | 仅客户端 |

**纪律：战斗结算逻辑只能写在 `main`，`client` 只做呈现与预测。** 任何"客户端算完再告诉服务端"的设计都会在双端强制的场景下变成作弊面。

### 1.4 协议版本

`PROTOCOL_VERSION` 是独立于模组版本的整数。规则：

- 任何包结构、字段语义、握手流程的不兼容变更 → +1。
- 纯服务端修复（不改协议）→ 不动。
- 客户端与服务端协议版本不一致 → **拒绝连接**，kick 消息写明双方版本与下载地址。

模组版本号（`0.1.0`）用于发布追踪，协议版本用于准入判断，两者不混用。

## 2. 分层架构

五个逻辑层，依赖方向严格单向：

```
表现层（client）  ──┐
                    ├──→ 会话层 ──→ 沙盒层 ──→ 存储层
协议层（main）    ──┘         │
                              └──→ 战斗层
```

| 层 | 职责 | 不允许做的事 |
| --- | --- | --- |
| **会话层** | 会话状态机、回合推进、提案协商、队伍、判定 | 不直接改玩家背包，不直接算伤害 |
| **沙盒层** | 快照冻结与恢复、配装构造、临时属性、场地进出 | 不感知比分与胜负 |
| **战斗层** | 1.8 / 现代两套结算、格挡、击退、护甲 | 不感知会话存在，只接受"这个玩家当前用哪套规则"的输入 |
| **协议层** | 握手、状态同步、GUI 数据、输入上行 | 不含业务判断 |
| **存储层** | 快照、日志、会话记录、原子写 | 不含业务判断 |
| **表现层** | 渲染、输入、预测 | 不做权威判定 |

**关键约束：战斗层不知道"会话"是什么。** 它只接受一个查询结果——"这个玩家这一 tick 用哪套战斗规则"。这样战斗层可以独立测试（纯函数式），也避免了战斗逻辑与会话生命周期纠缠。会话层负责回答这个查询，并在回合开始/结束时切换答案。

## 3. 会话状态机

### 3.1 状态与迁移

```
DRAFT ──→ NEGOTIATING ──→ FROZEN ──→ ROUND_READY ⇄ ROUND_ACTIVE
                  │                        │
                  └──→ EXPIRED             └──→ ROUND_SETTLED
                                                  │
                            ┌─────────────────────┴──────────┐
                            ↓                                ↓
                      （还有下一局）                    RESTORING ──→ ARCHIVED
                            │                                │
                            └──→ ROUND_READY            （异常）──→ VOIDED
```

| 状态 | 进入动作 | 崩溃时处理 |
| --- | --- | --- |
| `DRAFT` | 创建提案对象 | 直接丢弃（无副作用） |
| `NEGOTIATING` | 发送私聊、等待确认 | 丢弃并通知 |
| `FROZEN` | 写快照、写日志、清玩家状态 | **回滚**：按快照恢复 |
| `ROUND_READY` | 重建配装、传送、倒计时 | 回滚到快照 |
| `ROUND_ACTIVE` | 应用战斗规则、开启边界检测 | 回滚到快照，系列赛作废 |
| `ROUND_SETTLED` | 记录判定、清方块与掉落物 | 回滚到快照 |
| `RESTORING` | 剥离临时属性、写回快照、传送回原位 | 重新执行（幂等） |
| `ARCHIVED` | 归档日志、释放场地 | 无需处理 |
| `VOIDED` | 标记作废、通知 | 无需处理 |

### 3.2 关键设计：所有可恢复状态都必须能从磁盘重建

内存中不保存"唯一真相"。会话的每一次状态迁移，都先把目标状态写入日志，再改变内存与玩家状态。启动时只读日志，不读内存。

### 3.3 回合循环与"重置在开头"

```
ROUND_READY（重建开局状态）
   → 倒计时
   → ROUND_ACTIVE（应用战斗规则、启用边界）
   → 判定
   → ROUND_SETTLED（清方块、清掉落物、记比分）
   → 若未分胜负 → ROUND_READY（重建，不依赖上一局是否干净）
```

**"重置在开头"是硬要求**：即使某局的收尾被中断（崩溃、强退），下一局的正确性也不依赖上一局是否干净。这直接决定了恢复逻辑可以做成"重建"而不是"修补"。

## 4. 数据模型

六类持久化对象。字段清单是需求，不是代码结构。

### 4.1 会话记录（JSON）

| 字段 | 说明 |
| --- | --- |
| `sessionId` | UUID，全局唯一 |
| `stage` | 状态机当前状态 |
| `revision` | 每次迁移 +1，用于幂等判断 |
| `createdAt` / `updatedAt` | 时间戳 |
| `ruleSnapshot` | 冻结后的完整规则（见 4.2） |
| `ruleFingerprint` | 规则快照的 SHA-256，用于事后核对 |
| `participants[]` | 参与者列表（含队伍归属、角色、快照引用） |
| `teams[]` | 队伍定义（名称、颜色、出生区） |
| `arena` | 场地记录（维度、区域边界、基准快照引用） |
| `rounds[]` | 回合记录（序号、判定、比分增量） |
| `score` | 按队伍的比分 |
| `voidReason` | 作废原因（正常结束为空） |

### 4.2 规则快照

提案确认后的规则集合，**冻结不可变**。以 JSON 存储，字段与 v0.2 第 3.4 节的 A–G 七组一一对应。冻结后任何修改都视为新提案。

### 4.3 参与者记录

| 字段 | 说明 |
| --- | --- |
| `uuid` / `name` | 玩家标识 |
| `teamId` | 所属队伍 |
| `role` | 提案人 / 受邀人 / 参与者 / 观战者 |
| `snapshotRef` | 生存快照文件名 |
| `snapshotFingerprint` | 快照指纹 |
| `loadoutRef` | 配装引用 |
| `state` | 在线 / 离线 / 已淘汰 |
| `restored` | 是否已完成恢复（幂等标记） |

### 4.4 生存快照（NBT）

直接序列化玩家的相关 NBT 子树，而不是自定义结构。理由：原版玩家数据的字段最多、最容易漏，直接搬运原始 NBT 能最大限度保真，也天然兼容模组附加数据（如其他模组写在玩家身上的持久数据）。

需要额外记录、原版 NBT 不含的项：维度、队伍关系、权限组、物品冷却、无敌帧、摔落距离。

### 4.5 日志（JSONL）

每行一个事件，追加写：

| 事件类型 | 载荷 |
| --- | --- |
| `SESSION_CREATED` / `STAGE_CHANGED` | 会话 ID、前后状态、revision |
| `SNAPSHOT_WRITTEN` | 参与者、文件名、指纹 |
| `ROUND_STARTED` / `ROUND_ENDED` | 回合号、判定、比分 |
| `BLOCK_PLACED` / `BLOCK_REMOVED` | 位置、方块、放置者 |
| `RESTORE_STARTED` / `RESTORE_COMPLETED` | 参与者、结果 |
| `ANOMALY` | 任何"不该发生"的情况，供人工核查 |

### 4.6 存储位置与写入策略

```
<world>/pvpocket/
├── sessions/<sessionId>.json
├── snapshots/<sessionId>/<playerUuid>.dat
├── journal/<sessionId>.jsonl
└── arena/<arenaId>.baseline      ← 场地基准快照
```

**原子写**：所有文件先写临时文件 → flush → 原子重命名。避免"写了一半"的文件成为恢复依据。

**日志优先**：先追加日志再改状态。崩溃时最多丢失最后一条未完成的事件，恢复逻辑可据此判断是前进还是回滚。

## 5. 生存快照与恢复

### 5.1 冻结（进入沙盒前）

1. 校验：玩家不在其他会话、不在死亡状态、不在载具上（或记录载具）。
2. 序列化玩家状态 → 写临时文件 → 原子重命名。
3. 计算指纹 → 写入会话记录。
4. **写日志 `SNAPSHOT_WRITTEN`。**
5. 确认写入成功后，才允许改动玩家状态。

顺序不能颠倒。第 5 步之前任何一步失败，玩家状态都没有被触碰。

### 5.2 恢复（会话结束）

1. 读取快照，校验指纹。
2. 剥离所有带本会话标识的临时属性修饰。
3. 清空沙盒物品（带血缘标记的物品直接销毁，不进入生存）。
4. 写回玩家状态：背包、装备、副手、末影箱、经验、生命、饥饿、饱和度、效果、位置、维度、游戏模式、队伍、火焰、摔落距离、物品冷却。
5. 重新计算指纹并与快照比对。
6. 写日志 `RESTORE_COMPLETED`，标记 `restored = true`。

**第 5 步是自检，不是可选项。** 它能在恢复逻辑出错时立刻暴露，而不是等玩家上线发现物品少了。

### 5.3 局间恢复（每局开始）

不触碰快照。只做：

1. 清空当前背包与装备。
2. 按配装重新构造（物品、附魔、耐久、堆叠）。
3. 重置生命、饥饿、饱和度、效果（按配装与规则）。
4. 传送回出生点，重置朝向与速度。
5. 清除本回合的临时属性，重新施加。
6. 清除场地内掉落物与经验球。
7. 逆序移除本回合放置的方块。

**两级恢复互不依赖**：局间恢复失败不应该阻止会话恢复。

## 6. 战斗层接管点清单

这是本项目技术风险最集中的地方。8 个接管点，每个都要回答"未命中时是否安全"。

| # | 接管点 | 目的 | 安全默认 | 风险 |
| --- | --- | --- | --- | --- |
| 1 | 玩家攻击结算入口 | 跳过冷却缩放、按 1.8 武器伤害表取值 | 走原版 | 高（影响所有伤害） |
| 2 | 受击结算入口 | 1.8 护甲减伤公式、格挡减伤 | 走原版 | 高（影响所有受伤） |
| 3 | 击退合成 | 1.8 击退向量、冲刺加成、格挡减半 | 走原版 | 中高（体感敏感） |
| 4 | 暴击判定 | 1.8 的暴击条件 | 走原版 | 中 |
| 5 | 横扫生成 | 1.8 模式下禁用 | 走原版 | 低 |
| 6 | 右键使用（剑） | 进入/退出格挡态 | 走原版 | 中（与物品使用冲突） |
| 7 | 攻击冷却查询 | 客户端指示器与命中门限 | 走原版 | 低 |
| 8 | 耐久消耗 | 1.8 的消耗规则 | 走原版 | 低 |

**统一原则：白名单式接管。** 每个接管点先问"这个攻击者/受击者是否处于 legacy 回合"，不满足就直接调用原版逻辑，不做任何额外计算。这保证了"生存玩家永远走原版"这件事在结构上成立，而不是靠代码审查。

**接管点的实现方式优先级**：Fabric API 事件 > Mixin。能用事件解决的不用 Mixin，因为事件接口在版本升级时更稳定。预计 1、2、3 必须用 Mixin（没有对应事件），4–8 可能可以用事件或简单的注入。

**所有 Mixin 集中在两个包内**（主端 / 客户端各一个），不散落在业务代码里。版本升级时只需检查这两个包。

## 7. 1.8 数值对照表

### 7.1 工作方法

1. 反编译 Minecraft 1.8.9 服务端，提取战斗相关常量与公式。
2. 与 1.21.1（Yarn 映射）逐项对比。
3. 产出 `docs/data/1.8-combat-reference.json`，字段：机制、1.8 取值、1.21.1 取值、PvPocket 采用值、置信度。
4. 用单元测试锁定每个常量——**数值变了测试必须红**。

### 7.2 必须提取的项

| 类别 | 具体项 |
| --- | --- |
| 伤害 | 武器基础伤害表（全部工具/武器）、附魔加成公式、暴击倍率与条件 |
| 护甲 | 减伤公式、护甲值上限、韧性（应确认 1.8 是否存在） |
| 击退 | 基础水平/垂直分量、冲刺加成、击退附魔、击退抗性、格挡时的减免、空中受击修正 |
| 格挡 | 减伤比例、击退比例、移速惩罚、退出条件 |
| 耐久 | 每次命中的武器消耗、每次受击的护甲消耗 |
| 无敌帧 | 时长、同 tick 多段伤害的处理 |

**纪律：不凭记忆写数值。** 上面每一项都必须来自反编译结果或可引用的社区文档，并在对照表里标注来源。凭印象写出来的数字看起来合理，但会在体感上处处差一点，而差一点的东西最难定位。

## 8. 网络协议

### 8.1 握手

客户端在加入时发送握手包：`protocolVersion`、`modVersion`、能力位（是否支持自绘 GUI、是否支持预测渲染）。

服务端校验：

- 未收到握手包（原版客户端）→ 拒绝，kick 消息说明需要安装。
- `protocolVersion` 不匹配 → 拒绝，说明双方版本。
- 通过 → 登记该玩家的客户端能力。

### 8.2 下行（服务端 → 客户端）

| 包 | 时机 | 内容 |
| --- | --- | --- |
| 规则快照 | 提案确认 / 会话开始 | 完整规则（只读） |
| 会话状态 | 状态迁移时 | stage、回合号、比分、剩余时间 |
| 面板数据 | 打开 GUI 时 | 规则项定义、配装、队伍、玩家列表 |
| HUD 数据 | 每 200ms 或状态变化时 | 血量、倒计时、队伍、边界提示 |
| 场地边界 | 进入场地时 | 区域 AABB、允许的方块交互 |

### 8.3 上行（客户端 → 服务端）

| 包 | 内容 | 校验 |
| --- | --- | --- |
| 规则提交 | 完整规则 + 提案版本 | 服务端重算合法性，不信任客户端 |
| 配装提交 | 配装内容 | 服务端校验参数上限、物品池、附魔合法性 |
| 准备/接受/拒绝/编辑 | 意图 | 校验角色与状态 |
| 格挡输入 | 可选（若不做客户端预测则不需要） | 服务端以自身状态为准 |

**原则：下行同步状态，上行传递意图。** 不做"事件同步"（客户端说"我打了谁"），只做"意图同步"（客户端说"我想打"，服务端自己判定打没打到）。

## 9. GUI 架构

### 9.1 视觉语言（先定，再写界面）

> 已由 [`docs/zh/04-visual.md`](../../zh/04-visual.md) 取代（当时的文件名是 `PvPocket-视觉规范-v0.6.md`），本节仅保留历史记录。
> 现行规范：近黑表面五级阶梯、橙黄强调（`#F5A524`）、红色仅用于破坏性动作、圆角 4/6px、
> 全部状态切换 60–320ms 帧率无关过渡、禁用 emoji 与图形符号字符、文案一行一条信息。

| 维度 | v0.4（已废弃） |
| --- | --- |
| 面板 | 深色半透明底（约 85% 不透明）+ 1px 描边 + 圆角 4px |
| 强调色 | 单一强调色，用于选中态与主按钮 |
| 间距 | 8px 栅格，面板内边距 16px |
| 字号 | 两级：标题 12px、正文 9px（Minecraft 字体单位） |
| 状态 | 常态 / 悬停 / 按下 / 禁用 四态，禁用态降低对比度而非隐藏 |
| 层级 | 面板 < 对话框 < 提示气泡，最多三层 |

### 9.2 组件库（10 个基础组件）

面板、按钮、开关、滑杆、数值输入、文本输入、滚动列表、标签页、提示气泡、队伍分配器。

**实现顺序：文本输入与滚动列表优先。** 这两个最费时且被最多界面复用；先做扎实，后面是拼装。

### 9.3 布局与缩放

- 布局用固定像素 + 栅格，不用百分比（Minecraft GUI 的坐标系是缩放后的虚拟像素）。
- 每个界面声明"最小宽高"，低于阈值时切换为紧凑布局（减少列数、缩短标签）。
- GUI scale 1–4 与常见分辨率组合必须逐一截图验证。

### 9.4 输入焦点

自绘 GUI 必须自己管理焦点：Tab 切换、方向键导航、Esc 取消、Enter 确认、文本输入捕获键盘。**这是自绘 GUI 最容易遗漏的部分**，不做的话键盘用户完全无法操作。

## 10. 场地与方块

### 10.1 一个必须纠正的架构假设

Minecraft **不支持在运行时创建维度**。因此"每个会话一个维度"不可行。实际方案是：

> **一个固定的决斗维度，内部按网格划分为若干独立区域，每个会话占用一个区域。**

区域尺寸由规则决定（16–128 格），维度总容量决定并发会话上限（可配）。这个纠正会影响 v0.1/v0.2 中"口袋维度"的描述——语义不变（仍然是完全隔离的空间），但实现上是"专用维度内的独立分区"。

### 10.2 场地生命周期

| 阶段 | 动作 |
| --- | --- |
| 初始化 | 维度首次加载时，为每个区域生成平坦基底并保存**基准快照** |
| 占用 | 会话开始时分配空闲区域，标记占用 |
| 使用 | 禁止破坏基准方块；允许放置的方块记入变更集合 |
| 释放 | 按基准快照整块还原，清空实体与掉落物，标记空闲 |

**"按基准快照整块还原"比"逐项清理"可靠**：即使变更集合有遗漏，整块还原也能兜底。变更集合的作用是"局间还原"（每局结束），基准快照的作用是"会话结束兜底"。两层防护。

### 10.3 方块变更集合

- 结构：位置 → 方块状态 + 放置者 + 序号。
- 局间还原：按序号**逆序**移除（处理附着关系）。
- 允许拆除：任何参与者都可以拆集合内的方块（否则对手无法清除掩体）。
- 禁止：拆基准方块、在边界外放置、在出生保护区内放置。

### 10.4 放置途径穷举（唯一攻击面）

所有能产生方块的途径都必须走同一个记录入口：

| 途径 | 处理 |
| --- | --- |
| 玩家右键放置 | 记录 |
| 发射器/投掷器放置 | 记录 |
| 末影人搬运 | 拦截或记录 |
| 模组方块 | 走同一入口（要求所有放置最终经过方块设置事件） |
| 流体流动 | 默认禁止（规则可开，开启时记录） |
| 爆炸产生（如 TNT 引燃） | 不产生方块，仅移除 |

**如果某条途径绕过了记录入口，它就会在还原时残留。** 这是本设计的唯一攻击面，必须在集成测试里逐条验证。

## 11. 崩溃对账

启动流程（在玩家登录之前执行）：

1. 扫描 `sessions/` 下所有非 `ARCHIVED` / `VOIDED` 的会话。
2. 对每个会话读取日志，确定最后完成的迁移。
3. 若处于 `FROZEN` 之后的任何状态 → 执行恢复（幂等）→ 标记 `VOIDED`，原因 `SERVER_CRASH`。
4. 释放场地占用，按基准快照还原区域。
5. 清理残留实体与掉落物。
6. 写 `ANOMALY` 日志供人工核查。
7. 通知：玩家下次登录时收到"上一场决斗因服务器中断作废"的提示。

**幂等保证**：恢复动作带 `revision` 与 `restored` 标记，重复执行不产生副作用。即使对账在中途再次崩溃，下次启动仍能继续。

## 12. 性能预算

| 场景 | 目标 |
| --- | --- |
| 空闲（无会话） | 零常驻开销：不注册 tick 监听，不做区域扫描 |
| 单会话 2 人 | 每 tick 开销 < 0.1ms |
| 满员 16 人 / 4 会话 | 每 tick 开销 < 1ms，TPS 下降 ≤ 5% |
| 快照写入 | 单次 < 50ms（异步写盘，不阻塞主线程） |
| 局间还原 | < 200ms（可接受一次短暂卡顿，但需在倒计时内完成） |

**优化点**：边界检测只在有活跃会话时启用；区域判定先用区块级位图粗筛，再做精确 AABB；快照序列化在主线程完成，写盘异步。

## 13. 测试策略

| 类型 | 覆盖 | 工具 |
| --- | --- | --- |
| 单元测试 | 伤害公式、击退向量、护甲减伤、配装校验、规则合法性 | JUnit（纯函数，不依赖游戏） |
| 集成测试 | 会话生命周期、快照冻结与恢复、方块还原 | Fabric GameTest |
| 崩溃注入 | 在 8 个关键迁移点各杀进程 5 次，验证对账结果 | 外部脚本 + 启动校验 |
| 污染审计 | 每次测试后对比方块/实体/物品总量，确认无净增 | 世界快照对比 |
| 1.8 对照 | 同一场景位移曲线与 1.8 参考服务端比对 | 录制 + 数值比对 |
| 性能 | 满员场景 TPS 与 tick 耗时 | Spark / 内置计时 |

**验收门槛**：连续 50 次会话（含至少 10 次人为崩溃）后，所有参与者生存状态逐项一致，服务器内无沙盒遗留物。

## 15. 未决技术风险

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 1.8 击退体感偏差 | 公式对了但摩擦/衰减不对，体感仍差 | 位移曲线对照测试，而不是肉眼判断 |
| 接管点遗漏 | 某些伤害路径绕过战斗层（弹射物、爆炸、荆棘、凋灵） | 建立伤害来源清单，逐条覆盖；未覆盖走原版 |
| 属性修饰泄漏 | 崩溃后临时属性残留在玩家身上 | 带会话标识 + 启动全量剥离 + 恢复后自检 |
| 方块放置途径遗漏 | 某条途径未记录导致残留 | 基准快照整块还原兜底 + 途径穷举测试 |
| 客户端崩溃责任 | 强制双端后，客户端问题即服务器事故 | 崩溃日志收集指引 + 与主流渲染模组共存测试 |
| 反作弊冲突 | 无冷却连击被判定为异常攻击速度 | 与常见反作弊的白名单机制对接，作为已知限制披露 |
| Loom 版本升级 | 1.11.8 在后续 MC 版本可能不适用 | 每平台独立工程，升级互不影响 |
