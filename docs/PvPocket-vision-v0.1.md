## 1. 产品愿景与定位

### 1.1 一句话定位

> PvPocket 为 SMP 生存服务器提供一个"决斗口袋"：两名玩家可以随时发起一场有规则、有边界、零风险的单挑，在完全隔离的沙盒中使用自定义配装进行多局对抗，并可逐局开启 Legacy 1.8 战斗手感；决斗结束后，双方在生存世界的一切数据原封不动。

### 1.2 愿景展开

生存服务器的玩家普遍存在一个未被满足的需求：**想打一场"算数的架"，但不想付出代价**。

现有方案都不合适：在主世界互殴会掉装备、破坏地形、引发纠纷；开竞技服需要额外客户端、独立账号体系和另一套社交关系；使用领地内的"PVP 开关"只是取消了伤害，没有规则、没有赛制、没有配装公平性。

PvPocket 的判断是：**缺的不是"能打架的地方"，而是"一套可以随时进入、随时退出、不留下任何痕迹的对局机制"**。因此产品重心不在"战斗系统"本身，而在**隔离与恢复的确定性**。战斗只是被隔离的那件事。

### 1.3 设计信条

1. **隔离优先于功能。** 任何新功能若不能证明其状态可被完整回收，就不进入 MVP。
2. **服务端权威。** 判定、结算、恢复全部在服务端完成；客户端只负责呈现。客户端模组是"更好的体验"，不是"能否玩"的前提。
3. **默认拒绝。** 沙盒内的一切世界交互（方块、实体、容器、经验、掉落）默认被拦截，只有显式放行的行为才生效。
4. **失败要安全。** 任何异常路径的终点都是"把玩家安全送回生存状态"，而不是"让玩家留在沙盒里"。
5. **不做平台。** 不做匹配、不做排行、不做赛季、不做独立客户端。PvPocket 是一个**服务器内的功能件**，不是一款游戏。

### 1.4 明确的非目标

- 不是独立竞技服务器或小游戏平台。
- 不是匹配大厅 / 排队系统 / ELO 排位。
- 不是排行榜、赛季、赛事管理平台。
- 不是完整的 1.8 版本模拟器（详见第 5 章的保真度分层）。
- 不是通用"战斗 API"，不对外承诺给其他模组提供战斗规则扩展点（P2 再评估）。

## 2. 目标用户与核心场景

### 2.1 用户画像

| 角色 | 关注点 | 对产品的隐含要求 |
| --- | --- | --- |
| 服主 / 管理员 | 服务器稳定、数据不丢、不被玩家钻空子 | 崩溃可恢复、防复制、权限与冷却可配、日志可审计 |
| 普通玩家（参与者） | 开一局要快、规则要公平、打完不留后患 | 发起流程 ≤ 3 步、配装可选可存、结束后"什么都没变" |
| 技术型玩家（配装作者） | 能精细调参数、能分享配装 | 参数覆盖度、导入导出（P2） |
| 旁观者 | 能看、不添乱 | 只读旁观、不入场、不参与判定 |

### 2.2 核心用户故事

**US-01 发起与接受（P0）**
玩家 A 在生存中手持任意物品，向玩家 B 发起决斗请求，指定场地、赛制（BO1/BO3/BO5）、战斗模式与配装方案。B 收到带摘要的请求，可接受、拒绝或反向提议（改局数/改模式）。请求有超时。
*验收要点：请求信息完整可读；拒绝后有明确反馈；超时自动失效且不产生任何状态残留。*

**US-02 进入沙盒（P0）**
双方接受后，在倒计时内被送入场地，此时双方已加载各自配装，生存数据已被冻结保存。
*验收要点：进入瞬间背包内容即为配装内容；生存物品不出现在沙盒中；倒计时内可取消并完整退回。*

**US-03 多局对抗（P0）**
BO3 中，每局开始双方状态回到"该局开局设置"（满血、配装满耐久、效果重新施加、位置回到出生点），而不是回到系列赛开始时的状态。每局独立判定胜负。
*验收要点：第 2 局开始时，第 1 局消耗的耐久、药水、血量全部复原。*

**US-04 边界与判负（P0）**
玩家离开场地边界时，按配置执行"拉回"或"判负"。掉入虚空、被卡在方块中、超时未分出胜负，均有确定结果。
*验收要点：任何非正常结束都有明确判定与提示，不出现"卡住无法结束"的会话。*

**US-05 Legacy 1.8 对局（P0）**
同一服务器上，玩家 A 正在 legacy_1_8 决斗中（无攻击冷却、剑格挡生效、击退手感为 1.8），玩家 B 在主世界打怪仍是现代战斗（有冷却、有盾牌）。两者互不影响。
*验收要点：机制按玩家隔离；每局重新应用；会话结束后 A 立刻恢复现代机制。*

**US-06 完整恢复（P0）**
系列赛结束（无论胜负、退出、崩溃），双方回到决斗前的位置、游戏模式、生命、饥饿、经验、药水效果、背包、末影箱、队伍关系，且与决斗前逐项一致。
*验收要点：恢复前后做状态比对，差异为零；不存在"多出来的物品"或"少掉的经验"。*

**US-07 中途退出与崩溃（P0）**
玩家在决斗中断线，或服务器在决斗中崩溃。重连/重启后，系统依据日志把该玩家恢复到决斗前的生存状态，并给对手一个确定的结果（判胜/判负/择期重赛，可配）。
*验收要点：不出现"玩家卡在场地里"或"生存数据停留在沙盒状态"。*

**US-08 旁观（P1）**
第三方玩家以旁观身份进入场地观战，不参与判定、不能交互、不能被攻击，退出后无任何状态变化。
*验收要点：旁观者的生存快照不被创建（或创建后完全等价恢复）；旁观者数量有上限。*

### 2.3 核心循环

**会话循环（分钟级）**
发起 → 协商确认 → 冻结生存状态 → 载入沙盒 → 〔回合循环〕 → 系列赛结算 → 恢复生存状态 → 归档日志

**回合循环（1–5 分钟）**
重置到本局开局 → 倒计时 → 对抗 → 判定 → 记录本局结果 → 若未分胜负则回到"重置"

**对局内循环（秒级）**
移动 / 攻击 / 格挡 / 使用物品 → 服务端结算（战斗模式决定结算规则）→ 反馈给双方

**关键设计含义：**"重置"是回合循环的第一步而不是最后一步。这样即使某局异常中断（崩溃、强退），下一局的正确性也不依赖于上一局是否干净收尾——这是"每局重置"硬约束的实现基石。

### 2.4 价值主张

- **对玩家**：把"打一架"的成本从"可能损失全身家当"降到"点两下按钮"。
- **对服主**：把"玩家私斗引发的纠纷、地形破坏、物品损失申诉"从运营负担变成一条可审计的日志。
- **对生态**：为 SMP 提供一个可配置的"对抗场景"，而不要求服务器转型为竞技服。

## 3. MVP 范围

### 3.1 MVP 要做的（P0）

| 编号 | 能力 | MVP 的完成口径 |
| --- | --- | --- |
| M-1 | 发起 / 接受 / 拒绝 / 超时 | 双人流程闭环；请求摘要包含场地、局数、模式、配装；有频率限制 |
| M-2 | 场地与边界 | 至少一种场地承载方式可用；边界判定确定；出界规则可配（拉回/判负） |
| M-3 | 生存快照与恢复 | 背包、装备、副手、末影箱、经验、生命、饥饿、饱和度、效果、位置、朝向、游戏模式、队伍、火焰/摔落状态 全部可冻结与恢复 |
| M-4 | 沙盒隔离 | 方块变化、实体生成、掉落物、经验、容器交互、爆炸、流体、活塞 均不污染生存世界 |
| M-5 | BO1/BO3/BO5 | 赛制可配；每局开局重置生效；局间比分与赛点判定正确 |
| M-6 | 配装基础 | 装备槽、副手、物品栏布局、附魔、药水效果；配装以声明式数据保存与加载 |
| M-7 | 配装隔离 | 配装属性不写入生存物品；耐久消耗只在沙盒内结算 |
| M-8 | legacy_1_8 按局开关 | 逐玩家、逐局生效；生存玩家不受影响；每局重新应用、局末清除 |
| M-9 | 防滥用 | 权限节点、冷却、并发会话上限、物品/经验复制防护、死亡不触发原版惩罚 |
| M-10 | 持久化日志与恢复 | 正常结束、断线、崩溃三种路径均可安全恢复或回滚 |

### 3.2 MVP 明确不做的

| 不做 | 理由 |
| --- | --- |
| 观战系统 | 涉及第三方状态管理与场地准入，收益低于其隔离成本；P1 再做 |
| 配装分享 / 导入导出 / 云端配装库 | 需要序列化格式稳定后才值得做；过早固化格式会返工 |
| 场地模板与可视化编辑器 | 先用配置文件与指令搭建，模板化在场地模型稳定后做 |
| 客户端模组（任何形式） | MVP 必须验证"纯服务端可用"；客户端增强在 P2 单独立项 |
| 1.8 全量数值复刻（护甲公式、附魔表、药水数值） | 成本极高、收益递减；MVP 只做手感层 + 关键数值层（见 5.1） |
| 排行榜 / 统计面板 / 赛季 | 非目标 |
| 匹配、排队、跨服 | 非目标 |
| 自定义伤害类型、自定义附魔注册 | P2；MVP 用原版类型 + 倍率调整 |
| 与领地/保护插件的深度联动 | MVP 只做"绕过保护判定"的白名单机制，不做插件级 API 对接 |

### 3.3 P1 / P2 的进入条件

- P1 项进入开发的**前提**：M-3 与 M-10 的恢复路径已在崩溃注入测试中稳定通过。隔离不可靠时，任何新增功能都只是扩大污染面。
- P2 项进入开发的**前提**：配装数据格式冻结一个版本周期且无破坏性变更。

### 3.4 MVP 的"最小可信形态"

MVP 不是"功能齐全的决斗系统"，而是"一个可以被信任的隔离容器，附带一场能打完的决斗"。判定 MVP 成立的标准是：**连续 50 次会话（含至少 10 次人为崩溃/强退）后，所有参与者的生存状态与进入前逐项一致，且服务器内不存在任何沙盒遗留物。** 功能少不算失败，恢复不干净就是失败。

## 4. 关键领域概念

以下概念用自然语言描述，描述的是**语义与约束**，不是实现结构。

### 4.1 概念一览

| 概念 | 自然语言定义 | 生命周期 | 核心约束 |
| --- | --- | --- | --- |
| **决斗会话** | 一次完整的系列赛。从请求被接受开始，到双方生存状态恢复完成为止。它是持久化与崩溃恢复的最小单位。 | 创建 → 冻结 → 进行中 → 结算 → 恢复中 → 已归档 | 同一玩家同时只能存在于一个未归档会话中 |
| **回合** | 会话内的一局。拥有独立的开局状态、独立的胜负判定、独立的重置动作。 | 待开始 → 倒计时 → 进行中 → 已判定 | 回合的所有可变状态必须能从"开局设置"重建 |
| **配装** | 一套**声明式**的战斗配置：装备什么、副手什么、背包怎么排、有什么效果、属性是多少、允许做什么。它不是一组真实物品，而是一份"如何构造开局状态"的配方。 | 定义 → 选择 → 载入 → 丢弃 | 永不写回生存物品；相同配装 + 相同种子必须得到相同开局 |
| **场地** | 一个有边界、有出生点、有规则集的空间单元。它决定"在哪里打"和"什么行为被允许"。 | 定义 → 校验 → 占用 → 释放 | 同一场地同一时刻只能被一个会话占用 |
| **战斗模式** | 决定"这一局按哪套规则结算战斗"的声明，取值为 `modern`（服务器默认现代规则）或 `legacy_1_8`。 | 随会话声明 → 随回合应用 → 随回合清除 | 只对声明了 legacy 的会话内的参与者生效，绝不影响其他玩家 |
| **生存快照** | 玩家进入沙盒前，其生存状态的完整冻结副本。它是"原始真相"，也是恢复的唯一依据。 | 冻结 → 持有 → 恢复 → 销毁 | 快照写入成功后，才允许改动玩家状态 |
| **沙盒状态** | 玩家在场地内的临时状态：配装构造出的背包、临时属性、临时效果、临时位置。 | 由配装构造 → 随回合重建 → 会话结束时整体丢弃 | 与生存快照永不交叉写入 |
| **沙盒恢复** | 把玩家从沙盒状态带回生存状态的动作。分为两级粒度：**局间恢复**（回到本局开局）与**会话恢复**（回到生存快照）。 | 按需触发 | 两级恢复互不依赖；会话恢复必须可重复执行 |
| **判定** | 一局结束的原因与结果：击杀、出界、投降、超时、断线、崩溃。 | 产生 → 记录 → 影响比分 | 每种判定都必须有确定的默认处理，不存在"未定义" |
| **决斗日志** | 追加写入的事件序列，记录会话状态迁移、关键操作与判定结果。是崩溃恢复的输入。 | 追加 → 归档 | 只追加不修改；先写日志再改状态 |

### 4.2 概念之间的关系（叙述）

一个**会话**包含 1 个**场地**占用、2 名（未来可能 N 名）参与者、1 份**战斗模式**声明、2 份**生存快照**、若干**回合**。每个**回合**引用两份**配装**来构造开局，并在结束时产生一条**判定**。所有状态迁移都写入**决斗日志**。

**关键点：** 配装与快照是两类完全不同的东西——配装是"要变成什么样"，快照是"原来是什么样"。把它们混为一谈（例如"进入时直接改玩家背包，退出时再改回来"）是本项目最容易犯的架构错误，会直接导致复制物品与数据丢失。**PvPocket 的基本立场是：玩家对象在会话期间是"沙盒的宿主"，其真实生存数据不在它身上。**

### 4.3 战斗模式冲突规则（可配置）

当双方选择的模式不一致时，三种策略：

| 策略 | 语义 | 适用场景 |
| --- | --- | --- |
| `either_legacy` | 任一方选择 legacy 则本局为 legacy | 休闲服，倾向满足想打 1.8 的一方 |
| `challenger_decides` | 发起方决定 | 明确"挑战者定规矩"的社群 |
| `must_agree` | 必须双方一致，否则无法开始 | 竞技向，公平优先 |

默认建议 `must_agree`（最不容易引发争议），但作为可配项。注意：**该策略只在"本局采用哪种模式"上生效，不改变"模式只作用于本会话参与者"这一硬约束。**

## 5. Legacy 1.8 模式的实现选项对比

### 5.1 先厘清"1.8 模式"到底指什么

"1.8 战斗"在玩家语境中是一组体感的集合，而不是一个可精确移植的规范。必须先把保真度分层，否则会陷入"永远做不完"的范围蔓延。

| 层级 | 内容 | 体感贡献 | 实现难度 | MVP 是否做 |
| --- | --- | --- | --- | --- |
| **F1 手感层** | 无攻击冷却（连击即时生效）、1.8 击退曲线、剑右键格挡（减伤 + 减击退）、暴击与横扫规则、攻击音效 | 约 80% | 中（服务端可全接管） | **做** |
| **F2 关键数值层** | 武器基础伤害表、攻速属性、护甲减伤公式与韧性缺失、保护类附魔的减伤方式、耐久消耗速率 | 约 15% | 中高（需接管伤害结算管线） | **做核心项**（伤害表 + 护甲减伤） |
| **F3 全量复刻层** | 1.8 的全部附魔数值、药水数值、饥饿与回血节奏、实体碰撞箱、命中判定时序、网络包时序 | 约 5% | 极高，且部分不可能（依赖客户端预测） | **不做**，并在产品文案中明确 |

**结论：** MVP 承诺的是"F1 + 关键 F2"，对外表述为"1.8 手感近似"，而非"1.8 完全一致"。这条边界必须在文档与游戏内提示中写明，否则会持续收到"手感不对"的反馈而无法收敛。

### 5.2 关键技术判断（决定方案可行性）

在 1.21.1 的服务端权威模型下，以下几点决定了"按玩家动态开关"是否可能：

1. **攻击冷却在服务端结算。** 客户端只负责显示攻击指示器与预测动画，实际伤害由服务端按"距上次攻击的 tick 数 / 冷却时长"缩放。因此服务端完全可以做到"对 A 玩家不施加冷却、对 B 玩家施加冷却"。
2. **攻击指示器读取的是攻速属性。** 若通过属性把攻速调到极高，客户端指示器会自然表现为"瞬间充满"，视觉与服务端行为一致——这是纯服务端方案能获得可接受视觉反馈的关键。
3. **击退、暴击、格挡减伤、无敌帧窗口都在服务端结算点。** 可以被按会话接管。
4. **格挡的视觉表现无法纯服务端实现。** 原版客户端不会为剑播放格挡姿态（剑没有 use 行为），也不会显示"正在格挡"。服务端能实现**机制**，但**看不到动作**，只能用音效、粒子、动作栏提示补偿。
5. **第三方战斗模组绝大多数是全局配置。** 它们的设计前提是"整个服务器一套战斗规则"，没有"按玩家/按对局切换"的概念。

第 5 点是本方案对比的核心：**问题不在于"有没有现成的 1.8 模组"，而在于"现成的 1.8 模组几乎都是全局开关"。** 而全局开关直接违反硬约束——生存模式必须保持现代战斗。

### 5.3 三个方案对比

| 维度 | A. 依赖现有服务端模组 | B. 自研战斗规则层 | C. 混合（自研规则层 + 复用数值资产） |
| --- | --- | --- | --- |
| 代表实现 | CombatEdit（服务端 1.8 战斗，Apache-2.0）、Old Combat Mod、Classic Combat、Not Coldown（数据包） | PvPocket 内部按会话接管战斗结算 | 自研接管层 + 借用现有模组的数值表/配置作为基线 |
| 是否需要客户端安装 | 否（服务端生效） | 否（视觉有缺口，见 5.2-4） | 否 |
| **是否支持按玩家动态开关** | **否。** 这些模组以"服务器全局配置 / 世界级数据包"为模型，切换即全服切换 | **是。** 会话内参与者走 legacy 结算，其余走原版 | **是** |
| 能否按"每一局"重新应用 | 否（全局状态没有"局"的概念） | 是（每局开局重新施加，局末清除） | 是 |
| 崩溃恢复行为 | 模组自身无会话概念；崩溃后全局配置仍生效，与"决斗已结束"的事实脱节 | 由 PvPocket 日志驱动，重启后按会话状态重新施加或清除 | 同 B |
| 与自定义配装的兼容性 | 差。模组的属性/物品默认值改写与配装的临时属性会互相覆盖，来源不可辨 | 好。配装与规则层同源，属性变更带会话标记 | 好（需明确"谁的属性优先"） |
| 与生存模式的隔离性 | **不满足**（全局生效即污染生存） | 满足 | 满足 |
| 实现成本 | 低（接入即可） | 高 | 中高 |
| 维护风险 | 中（依赖第三方版本节奏；1.21.1 → 后续版本升级受制于人） | 中高（需跟进原版战斗管线变更） | 中高 |
| 反作弊兼容 | 好（模组作者通常已处理） | 需自行处理（见 8.1 R-06） | 需自行处理 |
| 结论 | **不可单独使用**，但可作为数值参考与兼容目标 | **推荐作为主路径** | **推荐的落地形态**：以 B 为主体，吸收 A 的数值资产 |

### 5.4 方案 A 的细节与致命点

调研到的可用资产：

- **CombatEdit**（服务端，1.19–1.26.x，Apache-2.0）：默认配置即"1.8 风格战斗"，可配置实体默认属性、物品属性修饰符、物品组件、攻击音效、是否启用 1.8 击退。它通过"改写实体/物品的**默认**属性"实现，并提供数据包与模组扩展点（可注册自定义基础配置档案与扩展）。
- **Old Combat Mod**（服务端，1.16.4+）：恢复旧战斗与旧挥击动画，客户端无需安装。
- **Classic Combat**（纯服务端）：移除命中冷却，武器恒定按最大攻击值结算。
- **Not Coldown**（数据包）：管理员级全局开关，在"1.8.9 无冷却"与"现代冷却"之间切换。

**致命点：** 这些方案的配置模型是"服务器/世界级的全局默认值"。CombatEdit 的扩展机制能让**模组作者**提供不同的配置档案，但档案的选择仍然是全局的；没有"玩家 X 现在用档案 A、玩家 Y 用档案 B"的语义。**因此它们无法满足"生存保持现代、决斗内 legacy"这一硬约束。**

**可用之处：** 它们的 1.8 配置档案（实体属性、物品属性修饰符、物品组件的具体数值）是一份经过实践检验的**数值基线**，可以作为 PvPocket 自研规则层的参考与对照测试基准。这构成方案 C 的合理内核。

**共存策略（必须明确）：** 如果服主的服务器上已经全局启用了这类模组，那么"生存模式保持现代战斗"这一前提在 PvPocket 之外就已经被破坏。PvPocket 应在启动时**检测并告警**，而不是假装兼容——否则玩家会把"生存也有 1.8 手感"归因于 PvPocket。

### 5.5 方案 B / C 的隔离层设计（保证生存不受影响）

自研规则层的核心不是"如何实现 1.8"，而是"如何保证只对应该生效的人生效"。三道闸：

**第一道闸：身份闸。** 每一次战斗结算，先问"攻击者与受击者是否都在某个声明了 legacy 的会话中，且该会话当前处于进行中的回合"。任一不满足，立即走原版路径，不做任何额外计算。这是最外层的开关，必须是**白名单式**（默认原版，命中条件才接管），而不是黑名单式（默认接管，排除某些人）。

**第二道闸：局闸。** 即使在会话中，模式也只在"回合进行中"生效。倒计时、局间、结算、观战阶段一律回到原版结算。这样"每局重新应用、每局结束清除"就退化为"回合状态机进入/退出时的一次幂等操作"，而不是散落在各处的条件判断。

**第三道闸：清理闸。** 所有为 legacy 模式写入玩家对象的临时状态（属性修饰、标记、临时规则）都必须带**会话标识**。服务器启动时执行一次全量扫描：任何带有未知/已归档会话标识的临时状态一律剥离。这是崩溃恢复的最后兜底——即使日志损坏，也不会留下永久的战斗规则污染。

### 5.6 推荐

**推荐方案 C：以自研按会话战斗规则层为主体，把现有模组的 1.8 配置档案作为数值基线与回归对照。**

理由：
1. 只有自研层能满足"按玩家、按对局、按局"三重粒度——这是硬约束，不可协商。
2. 现有模组的数值资产可以显著降低调参成本，且提供了一个"外部正确答案"用于对比测试。
3. 不引入运行时依赖，避免版本升级受制于人（1.21.1 → 1.21.x 的升级节奏由我们自己控制）。

**明确的风险：** 这是三个方案里实现成本最高的，且战斗结算管线的接管点较多（伤害计算、击退、格挡、暴击、无敌帧、耐久、音效），容易在边缘情况上出错。缓解方式见 8.1 与第 9 章的验证型原型安排。

## 6. 沙盒隔离与完整恢复的实现原则

这一章是产品的地基。原则的优先级高于任何功能。

### 6.1 九条原则

**P-01 单一真相源。**
生存数据只存在于生存快照，沙盒数据只存在于会话。两者之间只有两条受控通道：**冻结**（生存 → 快照，一次性）与**恢复**（快照 → 生存，一次性）。禁止任何"顺手改一下"的旁路写入。

**P-02 先写日志，后改状态。**
任何会改变玩家状态的操作，都必须在执行前把"意图"追加到日志。崩溃发生在任意时刻，恢复逻辑都能从"最后一条已完成的意图"推断出应该前进还是回滚。反过来（先改状态再记日志）会在崩溃时产生无法解释的状态。

**P-03 恢复必须幂等。**
会话恢复动作可以被重复执行任意次，结果一致。实现上依赖"会话标识 + 状态机阶段"两个维度：同一阶段重复恢复不产生副作用。这条原则直接决定了崩溃恢复能否安全地"多试一次"。

**P-04 属性用覆盖层，不写死。**
配装对玩家属性的影响（最大生命、移速、攻速、击退抗性等）以**带会话标识的临时修饰**形式存在，会话结束即整体剥离。绝不修改玩家的基础属性值，绝不把配装属性烘焙进生存物品。

**P-05 物品有血缘。**
沙盒内产生的一切物品（配装发放的、拾取的、合成的、掉落又捡回的）都带不可伪造的沙盒标记。标记物品出现在场地外 → 销毁并记日志；非参与者试图拾取 → 拒绝。生存物品进入场地 → 在冻结阶段就已离开玩家，物理上不可能出现。

**P-06 世界交互默认拒绝。**
场地内的方块破坏/放置、容器开启、流体流动、活塞推动、爆炸波及、实体生成、火焰蔓延、作物生长、红石跨边界传导，默认全部拦截。放行清单必须是显式枚举，且每一项都要回答"它会不会把状态带出场地"。

**P-07 死亡被接管。**
场地内的死亡不触发原版掉落、不触发重生惩罚、不产生可被他人拾取的掉落物、不写入生存死亡统计（是否计入统计为可配项）。死亡只产生一条判定，随后进入局间恢复。

**P-08 两级恢复互不依赖。**
局间恢复（回到本局开局）与会话恢复（回到生存快照）是两条独立路径。局间恢复失败不应该阻止会话恢复；会话恢复也不假设局间恢复已经执行过。

**P-09 异常路径优先"送回去"。**
任何无法判定的状态（数据不一致、日志缺失、场地损坏），默认动作是：把玩家恢复到生存快照、结束会话、记录一条待人工核查的告警。**宁可错判一局，不可留下一个卡在沙盒里的玩家。**

### 6.2 两级恢复的语义对照

| 维度 | 局间恢复（Round Restore） | 会话恢复（Session Restore） |
| --- | --- | --- |
| 目标状态 | 本局开局设置 | 生存快照 |
| 触发时机 | 每局开始前；每局结束后 | 会话结束（正常/异常/崩溃） |
| 数据来源 | 配装 + 场地出生点 + 本局参数 | 生存快照 |
| 覆盖范围 | 背包、装备、耐久、效果、生命、饥饿、位置、临时属性 | 全部生存状态（见 6.3） |
| 失败后果 | 本局作废，重新构建 | 玩家数据风险，最高优先级 |
| 可重复性 | 可（幂等重建） | 可（幂等回写） |

### 6.3 "完整恢复"的清单（逐项验收口径）

| 类别 | 具体项 | 备注 |
| --- | --- | --- |
| 物品 | 主背包 36 格、护甲 4 格、副手、光标手持物 | 逐格比对，含 NBT/组件 |
| 容器 | 末影箱内容 | 决斗中禁止访问末影箱，但仍需冻结以防其他途径变更 |
| 经验 | 等级、进度、总经验值 | 决斗中获得经验必须被拦截或丢弃，不可回流 |
| 生存指标 | 生命、最大生命、饥饿、饱和度、氧气、火焰状态、摔落距离 | 摔落距离易被忽略，会导致"回到主世界立刻摔死" |
| 状态效果 | 全部药水效果的种类、等级、剩余时长 | 剩余时长必须冻结，不能"重置为满时长" |
| 空间 | 维度、坐标、朝向、载具 | 若决斗前骑乘生物，需恢复骑乘关系 |
| 模式 | 游戏模式（生存/创造/冒险/旁观）、飞行状态 | 创造模式玩家发起决斗的行为需单独定义 |
| 社交 | 队伍、计分板队伍、权限组 | 队伍关系影响 PVP 判定，必须恢复 |
| 其他 | 冷却（物品冷却）、无敌帧、隐身/发光标记 | 物品冷却容易被遗漏 |

### 6.4 崩溃恢复的三种场景

| 场景 | 日志可见事实 | 处理动作 |
| --- | --- | --- |
| 服务器正常关闭 / 会话正常结束 | 会话处于"恢复中"或"已结算" | 完成或补齐会话恢复，归档 |
| 服务器崩溃（进程被杀 / 断电） | 会话处于"进行中"，回合未判定 | 启动时扫描未归档会话 → 全部回滚到生存快照 → 该系列赛作废（可配为"判发起方胜/无效"）→ 告警 |
| 玩家断线但服务器正常 | 会话进行中，某参与者离线 | 宽限期内等待重连；超时则判定该方本局负，继续系列赛；若双方均离线则终止会话并回滚 |

**重要取舍：** MVP 明确选择"崩溃后一律回滚，不做续赛"。续赛需要重建回合内的瞬时状态（血量、位置、效果剩余时长、掉落物），正确性远低于回滚，而收益仅是"少打一局"。这个取舍应在文档中写明，避免后续被当作缺陷。

### 6.5 场地承载方式（一个待决策的架构选择）

"场地"是逻辑概念，物理承载有两种：

| 承载方式 | 隔离确定性 | 每局重置成本 | 服主自建成本 | 可见性 | 风险 |
| --- | --- | --- | --- | --- | --- |
| **世界内区域**（主世界划一块地） | 中（依赖事件防火墙完备性，攻击面大） | 中（需记录并还原方块变化） | 低（就地搭建） | 高（旁边就能看） | 生物生成、流体、爆炸、他人误入、区块卸载、领地插件冲突 |
| **口袋维度**（独立维度，从模板生成场地） | 高（默认什么都不存在，无需拦截） | 低（按模板重建或整块还原） | 中（需先把模板导入） | 中（需传送，可旁观） | 维度注册、传送边界、玩家误留、跨维度数据一致性 |

**建议：** 逻辑上把"场地"与"承载"解耦（成本很低，且为未来留出空间），MVP **只实现一种承载**。若把"隔离确定性"作为第一优先级（符合 1.3 信条 1），建议 MVP 直接采用**口袋维度**——它把"事件防火墙是否完备"这个开放式风险，转化为"传送与维度管理"这个封闭式问题。若产品更看重"在自家主世界看得见的竞技场"，则选世界内区域，但必须接受防火墙需要长期打磨。

*此为本阶段需要确认的首要决策点（D-01）。*

## 7. 配装自定义参数清单与优先级

### 7.1 配装的三个语义规则

1. **声明式，不是实体。** 配装描述"如何构造开局状态"，不持有真实物品实例。这样同一配装被两个玩家同时使用时不会产生共享引用问题，也天然避免了"配装物品被带出场地"。
2. **可复现。** 相同配装 + 相同参数 → 逐项一致的开局状态。任何随机性（如附魔随机、耐久随机）必须来自显式种子。
3. **只读于沙盒。** 配装可以被编辑、复制、删除，但永远不会被"应用"到生存物品上。编辑配装与进行决斗是两条互不影响的路径。

### 7.2 参数清单

优先级：**P0** = MVP 必须；**P1** = 第二个迭代；**P2** = 可选增强。

| 类别 | 参数 | 优先级 | 默认策略 / 备注 |
| --- | --- | --- | --- |
| 玩家属性 | 最大生命上限 | P0 | 影响护甲与伤害换算，需与生命值同步设置 |
| | 当前生命值（开局） | P0 | 支持"残血开局"玩法 |
| | 移动速度 | P1 | 通过属性修饰实现，需限制上限防作弊式配装 |
| | 攻击速度 | P0 | legacy 模式下是核心参数（决定"无冷却"的等效值） |
| | 击退抗性 | P1 | 与 1.8 击退曲线叠加时需定义优先级 |
| | 自然回血开关 / 速率 | P1 | 影响长时间对局的可玩性 |
| | 饱食度 / 饱和度 | P1 | 与"是否允许进食"联动 |
| | 饥饿消耗速率 | P2 | 低优先级，多数对局用不到 |
| 护甲 | 护甲值（防御值） | P0 | 1.8 模式下走 1.8 减伤公式，现代模式走原版公式 |
| | 护甲韧性 | P1 | 仅现代模式有意义；1.8 模式下应被忽略并提示 |
| | 自定义防御倍率 | P2 | 用于非标准玩法（如"无甲"模式） |
| | 耐久上限 | P1 | 允许"无限耐久"作为特殊配装 |
| | 开局耐久 | P1 | 支持"残耐久"训练场景 |
| | 耐久消耗规则 | P1 | 可选：正常 / 不消耗 / 加速消耗 |
| | 附魔（含等级） | P0 | 需限制非法等级与冲突组合 |
| 武器 | 基础伤害 | P0 | 与武器类型解耦，允许"木剑高伤"这类自定义 |
| | 攻击速度 | P0 | 同上 |
| | 暴击倍率 | P1 | 1.8 与现代的暴击条件不同，需按模式区分 |
| | 自定义伤害类型 | P2 | MVP 用原版类型 + 倍率，避免注册新类型 |
| | 耐久上限 / 开局耐久 / 消耗规则 | P1 | 与护甲同构，可复用同一套语义 |
| | 附魔（含等级） | P0 | 同上 |
| 效果 | 药水效果列表 | P0 | 开局施加 |
| | 等级 / 时长 | P0 | 时长可设为"整局"（不倒数） |
| | 是否可被牛奶清除 | P1 | 影响对局节奏与反制手段 |
| | 局间是否重置 | P0 | 默认重置；"跨局累积"为特殊玩法 |
| 布局 | 快捷栏 9 格布局 | P0 | 决定开局手感 |
| | 背包 27 格布局 | P0 | 允许留空 |
| | 副手 | P0 | 1.8 模式下副手语义需明确定义（1.8 无副手） |
| | 装备槽（头/胸/腿/脚） | P0 | 允许空槽（"裸装"玩法） |
| | 堆叠数量 | P1 | 影响消耗品经济性 |
| 规则开关 | 是否允许拾取场地内物品 | P1 | 默认关闭（防污染与防"捡装备"） |
| | 是否允许合成 | P1 | 默认关闭 |
| | 是否允许破坏 / 放置方块 | P1 | 默认关闭；开启时需额外的还原机制 |

### 7.3 配装的边界约束

- **上限约束：** 属性类参数必须有服务器级上限（防止"移速 10 倍 + 攻速 100"的破坏性配装）。上限由服主配置，不由玩家决定。
- **合法性校验：** 附魔等级、效果组合、物品数量需在保存时校验，非法配装拒绝加载而不是"尽力加载"。
- **1.8 模式的语义冲突：** 部分参数（护甲韧性、副手、盾牌相关）在 1.8 模式下无对应语义。处理方式建议：**保留参数但不生效，并在配装编辑界面标注"此参数在 1.8 模式下被忽略"**——而不是静默忽略或报错。

## 8. 风险、开放问题与决策点

### 8.1 风险登记

| 编号 | 风险 | 影响 | 可能性 | 缓解 |
| --- | --- | --- | --- | --- |
| R-01 | 战斗规则层接管点不全，导致某些伤害路径绕过模式判定（如弹射物、爆炸、火焰、荆棘、凋灵伤害） | 中（模式不一致，玩家感知为"1.8 不生效"） | 高 | 建立"伤害来源清单"逐项覆盖；以"未覆盖即原版"为安全默认 |
| R-02 | 属性修饰泄漏，玩家回到生存后移速/血量异常 | 高（直接数据事故） | 中 | 带会话标识 + 启动时全量剥离 + 恢复后自检比对 |
| R-03 | 物品复制向量遗漏（漏斗、发射器、交易、潜影盒、死亡掉落、快捷栏切换、末影箱） | 高（经济破坏） | 中 | 沙盒物品血缘标记 + 场地内默认拒绝容器/红石交互 + 出界即销毁 |
| R-04 | 崩溃发生在"已改状态、未写日志"的窗口 | 高 | 中 | 严格先写日志；恢复逻辑可双向推导；定期注入崩溃测试 |
| R-05 | 与领地/保护插件冲突，导致场地内无法交互或保护被绕过 | 中 | 高 | 场地注册为受保护区域；提供"保护插件白名单/绕过"配置；文档明确支持矩阵 |
| R-06 | 反作弊误判：无冷却连击被判定为攻击速度异常 | 中高（玩家被封） | 中高 | 与常见反作弊的白名单机制对接；在 legacy 回合内向反作弊暴露"该玩家处于受控模式"的标记（需逐个适配，作为已知限制披露） |
| R-07 | 1.8 手感与玩家记忆不符，产生持续的"手感不对"反馈 | 中（口碑） | 高 | 明确 F1/F2 边界并在游戏内说明；提供参数化调校而非硬编码 |
| R-08 | 客户端无格挡动画，玩家不知道自己在格挡 | 中（可用性） | 确定 | 音效 + 粒子 + 动作栏状态提示；P2 客户端模组补齐 |
| R-09 | 服务器已有全局 1.8 战斗模组，前提被破坏 | 中 | 中 | 启动检测 + 告警 + 文档说明 |
| R-10 | 每 tick 边界检测与事件拦截带来性能开销 | 中 | 低中 | 只在会话进行时启用；按场地范围做空间索引；性能基线纳入验收 |
| R-11 | 原版版本升级导致战斗结算点变更 | 中 | 高（长期） | 接管点集中管理；建立"升级检查清单"；不承诺跨大版本无缝 |
| R-12 | 玩家利用"发起决斗"逃避死亡/追杀（战斗中发起即传送） | 中（玩法漏洞） | 中 | 战斗中禁止发起/接受；冷却；发起需双方均脱离战斗状态 |

### 8.2 开放问题

1. 决斗中的死亡是否计入生存死亡统计与成就？（建议：不计入，可配）
2. 创造模式玩家能否发起/参与决斗？其"生存快照"语义如何定义？（建议：MVP 仅允许生存/冒险模式）
3. 决斗中是否允许使用末影珍珠、床、重生锚等位移/爆炸道具？（属于配装规则，但影响场地设计）
4. 场地是否需要"环境危害"（岩浆、水、掉落伤害）？若需要，场地还原机制必须覆盖流体。
5. 多人混战（>2 人）是否在路线图上？当前所有设计按 2 人假设，若未来扩展，判定与快照模型需要预留（建议：MVP 明确按 2 人设计，但会话模型不写死人数）
6. 观战者能否在场地内飞行/穿墙/看背包？（P1 再定）
7. 配装是否允许玩家自由创建，还是只能从服主提供的白名单中选择？（影响防滥用与公平性）
8. 决斗日志的保留期与容量上限？（建议：结构化摘要永久保留，逐 tick 明细滚动删除）

## 9. 后续阶段建议

### 阶段 2：技术方案（下一步，仍不写业务代码）
产出《PvPocket 技术方案 v0.1》，必须回答：
- 战斗结算接管点的完整清单（伤害来源枚举 × 每条路径的处理方式），以及对未覆盖路径的安全默认。
- 生存快照的字段级定义与序列化格式（含版本号与向前兼容策略）。
- 日志模型：事件类型、写入时机、恢复推导规则、幂等保证。
- 场地承载方式的最终选择及其对隔离策略的影响（取决于 D-01）。
- 与常见服务端插件/模组的冲突矩阵（领地、经济、反作弊、死亡掉落、已有战斗模组）。
- 性能预算：边界检测、事件拦截、快照写入的频率与开销上限。

**建议在此期间完成 3 个技术验证型原型（spike）**，每个只验证一个假设、可丢弃：
1. **S-1 属性隔离验证**：给单个玩家加临时属性修饰 → 触发崩溃 → 重启后确认自动剥离。验证 R-02。
2. **S-2 按玩家战斗模式验证**：同一服务器上，A 无冷却连击、B 正常冷却，互不影响；A 退出后恢复。验证 5.2-1/2 的核心判断。
3. **S-3 崩溃恢复验证**：在"改状态前/改状态后写日志前/写日志后"三个时点强制杀进程，验证恢复结果一致。验证 R-04 与 P-02/P-03。

若 S-2 或 S-3 无法在可接受成本内通过，应回到本文件重新评估范围，而不是继续推进。

### 阶段 3：原型（可玩的窄切片）
只做一条路径：2 人、BO1、单一固定场地、单一固定配装、modern 模式。目标是打通"发起 → 进入 → 打完 → 完整恢复"的闭环，**功能可以极简，恢复必须完整**。

### 阶段 4：MVP 实现
按 M-1 ~ M-10 逐项实现，每完成一项即纳入回归集。建议顺序：快照与恢复 → 场地与边界 → 会话与回合状态机 → 日志与崩溃恢复 → 配装 → legacy 模式 → 防滥用。**legacy 模式放在靠后**，因为它依赖前五项全部可靠。

### 阶段 5：测试与验收
- **功能验收**：直接采用需求方给出的五条验收标准（现代冷却/1.8 冷却与格挡/双方机制互不影响/每局重置/无法复制/崩溃恢复）。
- **破坏性测试**：随机时点杀进程 × 50 次；断线重连 × 20 次；双人同时断线；场地内自杀；场地边界极限位移；背包满时恢复；末影箱非空时恢复。
- **污染审计**：每次测试后对比服务器内实体/方块/物品总量，确认无净增。
- **性能验收**：20 场并发会话（或服主配置上限）下 TPS 下降 ≤ 5%。

### 里程碑与停止条件

| 里程碑 | 判定 | 若不通过 |
| --- | --- | --- |
| G1 技术方案通过 | S-1/S-2/S-3 三个 spike 全部通过 | 收缩范围（如 MVP 先不支持 legacy，只做隔离决斗） |
| G2 原型闭环 | 连续 20 次会话恢复零差异 | 停止新增功能，专攻恢复 |
| G3 MVP 就绪 | 50 次会话含 10 次崩溃，污染审计通过 | 不上线，延长测试 |
