## 1. 配装系统

### 1.1 数据模型

配装是**一个槽位到物品条目的映射**，不是一串物品。原因：进战斗时要把东西精确放到指定位置（主手、头盔、快捷栏第 3 格），否则「配装一致」无法验收。

```
Loadout
└─ entries: List<LoadoutEntry>        // 上限 41 条（36 背包 + 4 护甲 + 1 副手）

LoadoutEntry
├─ id          String                // 稳定 id，用于 diff 与「改动了几项」
├─ category    WEAPON | EQUIPMENT | CONSUMABLE | BLOCK
├─ itemId      String                // minecraft:diamond_sword
├─ variant     String                // 材质/变体，可为 null
├─ count       int                   // 1..64
├─ slot        SlotRef               // 目标槽位
└─ spec        WeaponSpec | ArmorSpec | ConsumableSpec | BlockSpec
```

`SlotRef` 枚举：`MAINHAND` / `OFFHAND` / `HEAD` / `CHEST` / `LEGS` / `FEET` / `HOTBAR_0..8` / `INV_0..26`。

### 1.2 四类物品的规格

#### 武器 `WeaponSpec`

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| 武器类别 | 剑 / 斧 / 弓 / 弩 / 重锤 / 三叉戟 / 钓鱼竿 | 决定可用材质与可用特殊效果 |
| 材质 | 木 / 石 / 铁 / 金 / 钻石 / 下界合金 | **只影响贴图** |
| 伤害 | 0–50 | 覆盖物品的基础攻击力 |
| 耐久 | 1–10000 或 ∞ | ∞ 用原版 `unbreakable` |
| 击退 | 0.0–5.0，步长 0.1 | 不是附魔等级，是精确数值 |
| 横扫 | 0–3 级（0=关） | 仅现代模式生效，经典模式由 1.8 规则压制 |
| 火焰附加 | 0–3 级（0=关） | 两种模式都生效 |
| 无限 | 开 / 关 | 仅弓/弩 |
| 普通箭矢 | 0–64 | 无限开启时隐藏 |
| 特殊箭矢 | 种类 → 数量，可多条 | 仅弓/弩。种类取自原版 8 种药箭 |
| 命中伤害 | 开 / 关 + 0–20 | 仅钓鱼竿 |
| 激流 | 开 / 关 | 仅三叉戟 |

#### 装备 `ArmorSpec`

| 字段 | 取值 |
| --- | --- |
| 装备类别 | 头盔 / 胸甲 / 护腿 / 靴子 / 盾牌 |
| 材质 | 皮革 / 锁链 / 铁 / 金 / 钻石 / 下界合金（盾牌固定木质外观） |
| 护甲值 | 0–30 |
| 护甲韧性 | 0–20 |
| 耐久 | 1–10000 或 ∞ |
| 格挡减伤 | 0–100%（仅盾牌） |

#### 消耗品 `ConsumableSpec`

| 字段 | 取值 |
| --- | --- |
| 种类 | 常规食物 / 特殊食物 / 药水 |
| 常规食物 | 金胡萝卜、牛排、熟猪排、面包、烤马铃薯…（原版食物白名单） |
| 特殊食物 | 附魔金苹果、金苹果、牛奶桶、蜂蜜瓶 |
| 药水效果 | 效果 id + 时长(1–600 秒) + 等级(0–4)，可多条 |
| 数量 | 1–64 |

药水一律**喷溅型**，颜色由效果自动推算（多条效果时取第一个的颜色），不单独给颜色字段。

#### 方块 `BlockSpec`

| 字段 | 取值 |
| --- | --- |
| 种类 | 方块白名单（羊毛、木板、圆石、玻璃、黑曜石…） |
| 数量 | 1–64 |
| 双方不同颜色 | 开 / 关（仅羊毛、染色玻璃这类有 16 色的方块） |
| A 方颜色 / B 方颜色 | 16 色各选一 |
| 工具 | 镐 / 剪刀（作为条目附加，可设耐久与效率） |

「套娃」的落地方式：条目本身是「羊毛 ×64 + 双方不同颜色」，构造时按参与者的阵营序号取 `colorA` 或 `colorB`。所以一条配装定义，两边拿到的是不同颜色的同一堆方块。

### 1.3 属性怎么真正落到物品上

这是整个方案的技术核心。**不做自定义物品**——所有配装都构造成原版物品 + 组件覆写。这样渲染、动画、附魔光效、耐久条全部是原版行为，不会出现「自绘图标和真实手持模型不一致」。

| 属性 | 实现手段 | 备注 |
| --- | --- | --- |
| 外观材质 | 换基础物品 id | `diamond_sword` 与 `wooden_sword` 天然不同贴图 |
| 伤害 | 组件 `attribute_modifiers` 覆写 `generic.attack_damage` | **整表替换**而不是追加，否则会和物品默认值叠加 |
| 护甲值 / 韧性 | 同上，`generic.armor` / `generic.armor_toughness`，槽位 `armor` | 经典模式的护甲公式读 `getArmor()`，自动跟随 |
| 耐久 | 组件 `max_damage` + `damage=0`；∞ 用 `unbreakable` | |
| 横扫 / 火焰附加 / 激流 / 无限 | 组件 `enchantments` | 原版语义直接可用 |
| **击退（精确值）** | 自定义组件 `pvpocket:loadout_spec` + 攻击点注入 | 原版击退只有附魔等级（0.5 的整数倍），做不到 0.1 步长 |
| 药水效果与时长 | 组件 `potion_contents` 的 `custom_effects` | 不需要注册自定义药水，时长随便填 |
| 钓鱼竿命中伤害 | Mixin `FishingBobberEntity` 命中实体时结算伤害 | 原版钓鱼竿命中不掉血 |
| 盾牌减伤 | Mixin 玩家受击的盾牌分支，按配置比例改写 | |
| 配装来源 | 自定义组件 `pvpocket:loadout_spec` | 物品自带规格，客户端不需要查会话就能画 tooltip |

**为什么自定义组件是必要的**：击退要 0.1 精度、钓鱼竿要自定义伤害、盾牌要自定义比例，这三件事原版组件表达不了。把规格挂在物品上（而不是只存在会话里）还有一个副作用好处——战斗层读的是物品本身，玩家把武器丢给对手，对手拿到的就是同一把武器，行为一致。

**一个必须接受的限制**：`横扫` 只在现代模式生效。经典模式本来就没有横扫（S3 已经用 `noSweepForLegacy` 压制），所以面板上经典模式时这一行要置灰并写明原因，而不是让玩家填了却不生效。

### 1.4 配装与协商的关系

这是本方案里唯一需要你拍板的架构问题。三个选项：

| 方案 | 流程 | 代价 |
| --- | --- | --- |
| **A. 配装并入规则协商**（我推荐） | 发起方设规则 + 自己的配装 → 受邀方看到**双方配装**和规则 → 接受 / 改自己的配装 / 改规则重新征询 | 面板要多一个配装页；一次协商要传两份配装 |
| B. 规则同意后各自配装 + 准备确认 | 两段握手 | 多一轮交互；「准备」前改配装会绕过对方的同意 |
| C. 配装不协商，开打才可见 | 最省事 | **对手不知道自己答应了什么**，公平性直接没了 |

推荐 A 的理由：你原话是「进入后可以查看对方设置的规则，如果想要修改，就修改后重新向对方征求意见」。配装是比规则更直接影响胜负的东西，如果规则要同意而配装不用，这个同意就是残缺的。

A 的落地方式：`RULES_PROPOSED` 时附带发起方的配装指纹；面板新增「配装」入口，受邀方在里面看到自己的（可编辑）和对手的（只读）。接受时两份配装一起冻结进会话。

### 1.5 配装 GUI

复用规则面板的外壳与组件库，布局同构：

```
┌──────────────────────────────────────────────────────────┐
│ 配装            与 Dev2 的决斗            v1 · 3f2a91     │
├────────┬──────────────────┬──────────────────────────────┤
│ 武器   │ [icon] 钻石剑 ×1 │  材质   ◀ 钻石 ▶             │
│ 装备   │ [icon] 弓     ×1 │  伤害   ────●──── 7          │
│ 消耗品 │ [icon] 金苹果 ×3 │  耐久   ──●────── 500        │
│ 方块   │ [icon] 羊毛  ×64 │  击退   ●──────── 0.4        │
│        │ [icon] 镐     ×1 │  横扫   ◀ 0 ▶                │
│        │  + 添加          │  火焰附加 ◀ 1 ▶              │
├────────┴──────────────────┴──────────────────────────────┤
│ 已装备 12/41        装备到 ◀ 主手 ▶      [删除]  [返回]  │
└──────────────────────────────────────────────────────────┘
```

- **图标**：每行左侧用 `DrawContext.drawItem(stack, x, y)` 渲染真实物品图标。图标不是贴图资源，是把配装条目**在客户端构造一次**得到的 `ItemStack` 预览——和进战斗时服务端构造的是同一个函数，所以预览不可能和实物不一致。
- **右侧属性面板复用 `RuleRow`**：`RuleDefinition` 本来就是个「id + 标签 + 类型 + 范围 + 选项」的描述体，配装字段同样适用。这意味着滑杆、循环选择、开关、多选筹码一个都不用重写。
- **悬停提示**：不走原版 tooltip，用我们自己的气泡，内容是**按配置算出来的实际数值**（伤害 7、耐久 500/500、击退 0.4），而不是原版那套看不懂的「+3 攻击伤害」。
- **紧凑布局**：面板宽度低于 460 时，中间列表退化为纯图标（32px 宽），属性面板吃掉剩余宽度。

### 1.6 局间重置与防复制

「每小局结束恢复初始状态」在实现上是三层，缺一层就会出复制漏洞：

| 层 | 时机 | 动作 |
| --- | --- | --- |
| 1. 局间重置 | 每个 `ROUND_READY` | 清空背包 → 按配装重新构造 → 重置生命/饥饿/效果 |
| 2. 结算清场 | `ROUND_SETTLED` | 清除场地内所有掉落物与经验球 |
| 3. 快照恢复 | `RESTORING` | 生存快照整体覆盖 |

关键约束：**配装物品永远不进快照**。快照在 `freeze()` 时写，配装在 `startRound()` 时才发放，所以快照里没有它们；恢复时整体覆盖，配装物品自然消失。如果顺序反了（先发配装再快照），配装就会变成玩家的永久财产。

当前 BO1 下第 1 层是空转（只有一局），真正生效要等多局赛制（原 S7）。但代码路径要现在就按三层写，否则多局落地时会有一次返工。

### 1.7 校验与上限

`D-06` 定的是「创建无需权限」，所以配装必须靠上限兜底，否则任何人都能配出 50 伤害 + 5.0 击退 + 无限耐久的武器。

| 项 | 上限 | 处理 |
| --- | --- | --- |
| 条目数 | 41 | 超出丢弃并回一条提示 |
| 伤害 | 0–50 | 钳制 |
| 击退 | 0.0–5.0 | 钳制 |
| 护甲值 / 韧性 | 0–30 / 0–20 | 钳制 |
| 耐久 | 1–10000 或 ∞ | 钳制 |
| 附魔等级 | 0–5 | 钳制 |
| 药水时长 / 等级 | 1–600 秒 / 0–4 | 钳制 |
| 单包大小 | 16 KB | 超出直接丢弃整包 |
| 物品 id | 必须在白名单内 | 白名单外的条目丢弃 |

服务端一律**钳制 + 记日志**，不静默接受也不整包拒绝（除了超包）。

### 1.8 配装与规则的交叉校验

面板要主动提示矛盾组合，而不是让玩家开打才发现：

| 矛盾 | 提示 |
| --- | --- |
| `f.allowPlace = 关` 但配装里有方块 | 「本次规则禁止放置方块，这些方块用不了」 |
| `d.allowConsumables = 关` 但配装里有药水/食物 | 「本次规则禁止使用消耗品」 |
| `c.mode = 经典` 但配装里有盾牌 | 「经典模式无盾牌，建议移除或改用剑格挡」 |
| `c.mode = 经典` 且武器填了横扫 | 「经典模式无横扫，该设置不会生效」 |
| 弓没开无限且箭矢数为 0 | 「弓没有箭」 |

## 2. 场地

### 2.1 禁止刷怪

`doMobSpawning` 是服务器级游戏规则，关掉会影响主世界，所以不能用。现有 `dimension_type` 里的 `monster_spawn_light_level: 0` 只是把刷怪亮度门槛压到 0，**黑暗处照样能刷**。

方案：Mixin 拦截 `NaturalSpawner` 的刷怪入口，决斗维度直接返回。再加两道保险：

1. 维度初始化时清扫一次已有生物；
2. 区域释放时再清扫一次（防止有人在场地里用刷怪蛋或命令召唤）。

顺带覆盖史莱姆——史莱姆走的是同一条自然刷怪路径，拦一处即可。

### 2.2 区域边界与多房间

现在 `ArenaManager` 是硬编码的单场地（中心 `(4,0)`、半径 40、两个固定出生点）。要支持多房间，改成**网格分区**：

```
区域索引 i → 原点 (i % COLS) * PITCH, 0, (i / COLS) * PITCH
PITCH = 128 + 32 = 160      // 最大场地 128 格 + 32 格间隔
```

每个区域有自己的：

- 边界盒（由会话的 `e.sizeX / e.sizeZ / e.sizeY` 决定，不再用固定半径）
- 出生点（区域中心两侧对称）
- 占用状态（会话 id 或空闲）

配套改动：

| 项 | 现在 | 改成 |
| --- | --- | --- |
| `isInside(player)` | 固定圆心 + 半径 | 查玩家所在会话的区域边界盒 |
| `teleportToSpawn` | 固定两个坐标 | 区域原点 + 相对偏移 |
| `clearDroppedItems` | 整个场地范围 | 只清该区域（否则会误删隔壁房间的掉落物） |
| 边界可视 | 无 | 区域边缘一圈标记方块 + 越界提示 |

**这条改动是 S6 的硬前置**：不做分区，第二个并发会话会和第一个共用同一个空间，直接串场。

### 2.3 地图方块保护开关

新增规则 `f.protectTerrain`（默认**开**）：

| 值 | 行为 |
| --- | --- |
| 开 | 场地本体方块不可破坏；只允许拆除本次对局中玩家自己放置的方块 |
| 关 | 场地本体方块可以被破坏（战术挖掘、掩体破坏） |

实现走 `PlayerBlockBreakEvents.BEFORE`：位置不在本次会话的方块变更集合内 → 若保护开启则取消。

**一个必须一起做的前置**：关掉保护意味着场地会被挖坏，所以「关闭保护」必须和「按基准快照整块还原」同时上线（v0.4 §10.2 已设计但未实现）。否则一场关闭保护的决斗会把这个区域永久破坏，后续会话进到一个坑里。这两件事不能拆开做。

## 4. 需要你确认的 9 个问题

1. **「护眼附件」= 火焰附加？**（见 §0.2）
2. **「变价」= 边界？**（见 §0.2）
3. **「集中式造成伤害」= 击中式造成伤害？**（见 §0.2）
4. **配装是否纳入协商、对手可见？** 我推荐方案 A（见 §1.4）。这是影响最大的一条。
5. **经典模式下盾牌怎么办？** 三个选择：直接禁用 / 按 1.8 剑格挡规则工作（减伤 50%）/ 可配置减伤比例。我倾向第二个。
6. **激流要不要「陆地也能冲」？** 原版激流必须在水里或雨中，场地上没有水就完全用不了。
7. **属性上限的具体数值**（§1.7 的表格）是否合适？特别是伤害 0–50、击退 0–5.0。
8. **「地图方块保护」关掉后，是否同意先做「基准快照整块还原」再开放这个开关？** 否则场地会被永久破坏。
9. **配装是否要「预设」功能**（保存/读取几套常用配装）？你没提，但每次重新配一遍很痛苦。我建议放到下一版。

| 部分 | 相对成本 | 说明 |

## 7. 落地记录：S6 / S7a 实际做法与本文档的差异

> 这一节是在 S6 与 S7a 写完之后补的。上面的 §1–§4 保持原样不动，作为当时的判断；下面记录**实际做成了什么**、**哪些假设被推翻了**、**哪些问题还悬着**。

### 7.1 已落地

| 文档里的计划 | 实际做法 | 差异原因 |
|---|---|---|
| S6a 网格分区 | 4×4 网格，PITCH=160，最大地块 128×128 | 一致 |
| S6b 禁刷怪：Mixin + 两次清扫 | 三道门：`SpawnHelper.spawn` + `SpawnHelper.populateEntities` + 每 3 秒清扫 | **多了一道**。§2.1 只算到自然生成，实测发现区块首次生成时的被动生物播种（`populateEntities`）是另一条路径，一个 48×48 地块会一次冒出 7 只动物 |
| S6c `f.protectTerrain` + 基准快照整块还原 | `f.protectTerrain` + **偏差集合**回写基线 | **基准快照不需要存**。维度生成器固定（基岩/石头/空气三层），基线是可推导的纯函数，省掉了一个新的存储对象和它的崩溃一致性设计 |
| S7a 自定义组件 `pvpocket:loadout_spec` | 只用原版组件覆盖 `attribute_modifiers` / `max_damage` / `unbreakable` / `enchantments` / `potion_contents` | 原版组件能覆盖 90% 的需求，自定义组件留到真有做不到的需求时再加（见 §7.4） |
| §1.7 伤害上限 0–50 | 1.0–40.0 | 40 已经超过任何原版武器的两倍，再高没有实际意义 |

### 7.2 对 §4 九个问题的暂定答案

文档发出后没有收到逐条答复，为了不阻塞开发，S6/S7a 按下面的假设实现。**每一条都可以推翻，改动成本已标注。**

| # | 问题 | 暂定 | 改动成本 |
|---|---|---|---|
| 1 | 护眼附件 = 火焰附加？ | 未实现该开关，等确认 | 低（加一个 `WeaponFlag` 枚举值） |
| 2 | 变价 = 边界？ | **按"边界"理解**，已实现为每块地独立的 AABB | 已落地 |
| 3 | 集中式 = 击中式？ | 按"击中时造成伤害"实现（钓鱼竿靠 `attack_damage` 属性） | 已落地 |
| 4 | 配装纳入协商？ | **暂未纳入**。双方各自拿默认预设，看不到对方 | 中（S7c） |
| 5 | 经典模式盾牌 | 暂未特殊处理，走原版格挡 | 中（要 Mixin `(1+x)*0.5`） |
| 6 | 激流陆地可用？ | 暂未处理，原版规则（需水或雨） | 低 |
| 7 | 属性上限数值 | 伤害 1–40、护甲 0–30、耐久 ≤10000、击退 0–3 | 低（改常量） |
| 8 | 先做还原再开放保护开关 | **同意并已这样做**：偏差集合回写与开关同一批上线 | 已落地 |
| 9 | 配装预设保存/读取 | 未做 | 中 |

### 7.3 新增的、文档里没预料到的问题

1. **开局误判出界**。客户端首次下载一个新维度要 10–20 秒，期间可能把传送前的位置报回服务端，被判"出界"直接输掉。已加开局宽限期（`max(10s, a.countdown)`）内一律拉回不判负。**未在真实客户端复验。**
2. **`purge` 与实体加载有竞态**。租地时立刻清实体可能漏掉尚未 entity-load 的区块，靠 3 秒后的清扫兜底。
3. **`a.countdown` 只实现了"宽限"这一半**，"锁定移动"那一半还没做。

### 7.4 自定义组件还欠的三件事

原版组件覆盖不到、目前是缺口而不是妥协的：

1. **击退精确到 0.1** —— `knockback` 附魔只有 0.5 步进。如果"击退 0.3"是硬需求，就必须上自定义组件。
2. **盾牌减伤比例可配置** —— 1.8 格挡的减伤是硬编码 `(1+x)*0.5`，改成可配置需要 Mixin + 组件。
3. **钓鱼竿"只在击中时造成伤害"** —— 现在是通过 `attack_damage` 属性实现的，实际生效，但无法表达"只有击中才算"这个语义。

三件事都指向同一个组件，等需求确认后一次性做，比现在各做一半划算。
