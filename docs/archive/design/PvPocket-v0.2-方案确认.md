## 1. 需要澄清的两处

### 1.1 "崩溃" ≠ "死亡后重置"

你第 5 条描述的是**回合重置**，它是正常流程的一部分：

> 一方死亡 → 本局结束 → 判定 → **重置双方物品与背包、清除场地内玩家放置的方块与所有掉落物** → 下一局

而我在 v0.1 里说的"崩溃"指另一件事：**服务器进程异常终止**（断电、被 kill、JVM 崩溃、OOM）。此时玩家可能正站在维度里，生存快照在磁盘上，内存里的沙盒状态全部丢失。

两者处理方式完全不同：

| | 回合重置 | 崩溃对账 |
| --- | --- | --- |
| 触发 | 一方死亡 / 出界 / 投降 / 超时 | 服务器启动时发现"有未归档的会话" |
| 处理时机 | 对局进行中 | 服务器启动阶段，玩家登录之前 |
| 处理内容 | 重建开局状态、清方块、清掉落物 | 把玩家恢复到生存快照、把维度标记为待清理 |
| 能否省略 | 不能 | **不能**（否则玩家卡在维度里，生存数据停留在沙盒状态） |

**结论：回合重置按你的描述执行，没有问题。崩溃对账是必须做的事，但策略需要你确认——见 Q-1。**

### 1.2 只做"无冷却 + 格挡"之后，"1.8"这个词不再准确

1.8 的体感由三部分构成：连击节奏、击退位移、右键格挡。你保留了一头一尾，去掉了中间的击退。

实际手感会是：**点击即出伤，但被打的人飞出去的弧度是现代版的**。1.8 的击退垂直分量更高、水平位移更大，玩家对"打飞"的记忆很具体。去掉之后，老玩家会反馈"还是不像"。

这不是反对，是提示预期管理。建议对外统一改称：

> **经典战斗（无攻击冷却 + 剑格挡）**

而不是"1.8 模式"。措辞即范围声明，能挡掉大量"你这不叫 1.8"的对比。

另外需要明确一个细节：**剑格挡自带击退减免**。1.8 里格挡同时降低 50% 伤害和击退。如果你说的"只做格挡"包含格挡的完整效果，那击退减免作为**格挡属性**保留（而不是全局击退曲线），逻辑上是一致的。**默认按"包含击退减免"实现**，如需只减伤请指出。

## 2. 因决策变化而改写的设计

### 2.1 场地：从"区域"变为"维度内的可配置空间"

- 每个会话占用维度内一块由规则指定尺寸的空间（长 × 宽 × 高可配）。
- 场地本体由系统生成（平坦基底 + 边界），**不可破坏**。
- 场地模板（预设角斗场）**本期不做**，但生成逻辑要留出"按模板生成"的入口，否则 P1 要重写。
- 边界规则：离开边界 → 拉回或判负（规则可配）。
- 维度生命周期：会话创建 → 分配空间 → 会话结束 → 空间回收（清空实体、清空方块变更、标记可复用）。

**新增风险：** 维度内空间回收不彻底会导致"上一场的方块残留到下一场"。缓解方式是"会话结束即整块重置为生成态"，而不是"逐项清理"。

### 2.2 客户端：从"可选"变为"必需"，但要定义"没装的人怎么办"

双端模组带来两个必须回答的问题：

**问题一：未安装客户端的玩家能否进入服务器？**

| 方案 | 描述 | 对 SMP 的影响 |
| --- | --- | --- |
| A 强制 | 服务器要求全员安装，未安装直接踢出 | 门槛极高，多数 SMP 无法接受 |
| **B 功能受限** | 未安装者可正常生存，但无法发起/接受决斗 | 推荐。服务端在握手阶段检测，决斗入口对其关闭 |
| C 降级 | 未安装者可用指令走完流程，无 GUI | 体验差，但保留了可用性 |

建议 B。技术上需要在连接握手阶段做"客户端是否注册了本模组通道"的检测，这属于阶段 2 的网络设计。

**问题二：客户端能多做哪些事？**

这是双端带来的直接收益，也是当初建议纯服务端时缺的那部分：

| 能力 | 纯服务端 | 双端 |
| --- | --- | --- |
| 格挡姿态与格挡 HUD | 无 | 有 |
| 攻击冷却指示器准确性 | 近似 | 精确 |
| 规则设置 GUI | 无（只能指令） | 有（自绘面板） |
| 配装编辑 GUI | 无 | 有 |
| 倒计时 / 比分 HUD | 用 title/bossbar 凑 | 原生 |
| 区域边界可视化 | 粒子凑 | 原生渲染 |
| 客户端预测（格挡即时反馈） | 无 | 有 |

### 2.3 战斗模式：范围收窄后的实现清单

只保留两项，实现面比 v0.1 小得多：

| 项 | 实现要点 | 服务端/客户端分工 |
| --- | --- | --- |
| 无攻击冷却 | 回合内对参与者跳过冷却缩放，伤害按满值结算 | 服务端结算；客户端隐藏/重置指示器 |
| 右键格挡 | 持剑右键进入格挡态；减伤 50%；减击退；松开或切换物品退出 | 服务端判定减伤；客户端渲染格挡姿态与音效 |

**明确不做：** 击退曲线、暴击条件、横扫规则、护甲减伤公式、武器伤害表、附魔数值、药水数值、命中判定时序。

**保留的隔离要求不变**：只对声明了经典战斗的会话内、且回合进行中的参与者生效；生存玩家永远走原版。

### 2.4 验收标准修订

原验收标准中有一条需要改写：

| 原表述 | 修订后 |
| --- | --- |
| 进入 legacy_1_8 决斗后冷却消失、**剑格挡生效、击退手感变化** | 进入经典战斗决斗后**攻击冷却消失、右键格挡生效（减伤与减击退）**；击退保持服务器现代规则 |

其余四条（双方机制互不影响、每局重置、无法复制、崩溃恢复）保持不变。

## 3. 新增设计 A：规则提案与协商

这是本期新增的、逻辑最复杂的子系统。核心是**提案版本化**。

### 3.1 角色与状态

- **提案人**：当前持有规则版本的人。最初是发起者，任何人编辑后即成为新提案人。
- **受邀人**：1..N 人。
- **提案状态**：`草拟` → `待确认` → `全员接受` → `已开始`；旁支状态 `已拒绝` / `已过期` / `已撤回`。

### 3.2 流程

1. 发起者执行指令并指定目标玩家（支持多人），弹出**规则设置面板**（自绘）。
2. 在面板内配置全部规则（清单见 3.4），提交后生成**提案 v1**。
3. 系统向每个受邀人发送一条私聊消息，内含提案摘要（对手、赛制、模式、人数、场地尺寸）与"查看详情"入口。
4. 受邀人打开详情面板，有三个动作：
   - **接受** → 记录该人已接受，等待其余人。
   - **拒绝** → 该人退出本次邀请；若剩余人数低于该规则要求的最低人数，提案终止。
   - **编辑** → 打开同一套规则面板，修改后提交为**提案 v2**。
5. **任何编辑都会让此前所有"接受"全部作废**，所有人都要重新确认。这是本设计最重要的一条规则。
6. 全员接受 → 进入开局倒计时 → 规则快照冻结 → 会话开始。
7. 超时（可配，默认 60 秒无操作）→ 提案过期，所有人收到通知。

### 3.3 必须固化的五条约束

| 约束 | 理由 |
| --- | --- |
| **编辑即重置确认** | 否则会出现"我同意的是 v1，实际执行的是 v3" |
| **规则快照不可变** | 会话开始后规则冻结，日志记录快照指纹，事后可核对 |
| **同一玩家同时只能参与一个提案** | 避免"A 同时在跟 B、C 协商两套冲突规则" |
| **全员同意才可开始** | 与 D-04（模式必须双方同意）保持一致；规则是共享的，不能多数决 |
| **提案人与受邀人使用同一套面板** | 只读/可编辑由权限位控制，避免两套 UI 逻辑漂移 |

## 4. 新增设计 B：多人队伍

### 4.1 队伍模型

- 创建会话时通过指令或面板划分队伍，每队有名称、颜色、出生区。
- 约束：队伍数 1–4，每队 1–4 人，总人数 ≤ 16（均可配，受服务器上限约束）。
- 可选"各队人数必须相等"，避免 3v1 的失衡对局。

### 4.2 判定与比分

- **胜负：最后存活队伍获胜。** 某队全员出局（死亡/出界/投降）即淘汰。
- 生命模型：**个人独立生命**（MVP）。每人的死亡单独判定，队伍最后一人出局时整队落败。
- 比分按**队伍**记录，不按个人。BO3 即某队先赢 2 局。
- 局内击杀数、伤害量可选记录（用于战后统计展示，不参与判定）。

### 4.3 队伍带来的新增复杂度（必须正视）

| 问题 | 处理 |
| --- | --- |
| 出生点布局 | 每队一个独立出生区，圆形/线性分布在场地边缘，避免开局互相卡位 |
| 配装分配 | MVP 每人独立配装；"每队统一配装"作为可选项（实现成本高，建议 P1） |
| 断线处理 | 宽限期（默认 30 秒）内等待重连；超时则该玩家本局出局；若全队离线则整队出局 |
| 观战 | 被淘汰者转为观战，不可交互、不可复活（可配"允许复活"） |
| 快照数量 | 每个参与者一份生存快照，人数线性增长。恢复必须逐个成功，部分失败要有明确策略 |
| 友伤 | 关闭时队伍内伤害完全免疫；开启时按正常规则结算 |

**性能提示：** 16 人同时在场，边界检测、事件拦截、状态同步的开销是 2 人场景的 8 倍。性能预算需要按上限而非平均值来定。

## 5. 新增设计 C：方块放置与还原

### 5.1 核心机制：变更集合

整个机制只依赖一个数据结构——**本回合的方块变更集合**，记录"谁在哪个位置放了什么方块"。

| 操作 | 是否允许 | 处理 |
| --- | --- | --- |
| 破坏场地本体方块 | **禁止**（拦截） | 无副作用 |
| 放置方块（规则允许时） | 允许 | 记入变更集合，标注放置者 |
| 拆除**变更集合内**的方块 | 允许（任何参与者） | 从集合移除；该位置恢复为空气 |
| 拆除场地本体方块 | **禁止** | 拦截 |
| 爆炸摧毁变更集合内方块 | 允许（若开启爆炸物） | 从集合移除；掉落物归入待清除 |
| 爆炸波及场地本体 | **不破坏** | 拦截 |

### 5.2 还原规则

- **时机**：每局结束（无论何种判定）。
- **顺序**：按放置的**逆序**移除。这是为了处理依赖关系——例如玩家在自建的方块上放了火把，先拆方块会导致火把掉落。
- **范围**：只处理变更集合内的方块，不触碰场地本体。
- **清理**：同时清除场地内所有掉落物与经验球（含玩家死亡掉落、方块掉落、配装丢弃物）。
- **验证**：还原后校验"变更集合为空"，非空则告警（说明有遗漏路径）。

### 5.3 为什么这个设计是安全的

因为它把"还原"从"对比整个场地的方块差异"简化成了"遍历一个我们自己维护的列表"。前者需要知道场地原始状态、处理流体/方块实体/附着物，后者只需要一个集合。

**代价**：如果某个方块变更没被记入集合（遗漏的放置途径），它就会残留。所以所有"能产生方块"的途径都必须走同一个入口——包括发射器放置、末影人搬运、模组方块。**这是本设计的唯一攻击面，需要在技术方案阶段做穷举。**

## 6. 新增约束：GUI 自绘

### 6.1 约束的含义

- 不使用原版按钮/滑条的默认皮肤（那套 widgets 九宫格）。
- 不引入 owo-lib、Cloth Config、YACL、SpruceUI 等 UI 库。
- 不硬依赖 ModMenu（它是可选的入口，不是前置）。

**需要你确认的界定**：Fabric API 属于平台级基础依赖（几乎所有 Fabric 模组都依赖），我按"不算前置依赖"处理；如需连 Fabric API 也不用，则需改用 Mixin 直连原版，成本会显著上升。**默认按"允许 Fabric API，禁止其他第三方库"执行。**

### 6.2 需要自建的基础组件

| 组件 | 复杂度 | 说明 |
| --- | --- | --- |
| 面板背景 | 低 | 建议代码绘制（圆角矩形 + 半透明底 + 描边），避免贴图分辨率问题 |
| 按钮 | 低 | 常态/悬停/按下/禁用 四态 |
| 开关 | 低 | 布尔值 |
| 滑杆 | 中 | 数值范围 + 步长 + 实时回显 |
| 数值输入 | 中 | 键盘输入 + 校验 + 上下限钳制 |
| 文本输入 | **高** | 光标、选区、复制粘贴、退格、长度限制（原版有现成的，但要自绘就得自己实现） |
| 滚动列表 | **高** | 虚拟化、滚动条、惯性、边界回弹 |
| 标签页 | 中 | 规则项很多，必须分组 |
| 提示气泡 | 中 | 悬停显示规则说明 |
| 队伍分配器 | 中 | 拖拽或点选把玩家分配到队伍 |

### 6.3 风险与建议

**这是本项目最大的工作量黑洞之一，估计占总工期的 25–35%。** 三个建议：

1. **先定视觉语言，再写界面。** 深色半透明面板 + 单一强调色 + 8px 间距栅格 + 两级字号。定下来之后所有界面复用同一套组件，而不是每个界面各画一遍。
2. **组件库优先于界面。** 先花时间把 10 个基础组件做扎实（尤其是文本输入和滚动列表），后面 5 个界面就是拼装。
3. **GUI 缩放必须早测。** 自动 GUI 缩放从 1 到 4，玩家分辨率从 1280×720 到 4K，布局要在这些组合下都不破。这是自绘 GUI 最常见的翻车点。
